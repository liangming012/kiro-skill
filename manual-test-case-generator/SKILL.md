# 手工测试用例生成器

## 触发场景

当用户需要生成手工执行的测试用例时，使用此 skill。测试用例可以基于需求文档、代码改动，或两者结合来生成。包括：
- 用户说"生成测试用例"、"写测试用例"
- 用户说"根据文档写用例"、"根据需求文档生成用例"、"根据 PRD 写测试"
- 用户说"生成冒烟测试"、"写冒烟用例"
- 用户提到"手工测试"、"手动测试"
- 用户说"帮我出一份测试用例"

## 输入源判定（最先执行）

在开始任何工作之前，先判断本次生成测试用例的输入源。输入源决定后续的工作流走向，共有三种：

| 输入源 | 判定条件 | 生成依据 |
|--------|----------|----------|
| **仅文档** | 用户提供了需求文档（PRD、需求描述、设计稿说明、文档路径、粘贴的需求文本等），且当前无可用的代码改动或用户明确说只按文档 | 完全基于文档中描述的功能与业务规则生成用例 |
| **仅代码**（原有模式） | 用户未提供文档，仅要求基于分支/版本/提交的代码改动生成 | 基于 git diff 分析代码改动生成用例 |
| **文档 + 代码** | 用户既提供了需求文档，又存在可分析的代码改动（或明确要求结合两者） | 以文档为需求基准、以代码为实现事实，交叉比对后生成用例 |

**判定规则：**

1. 如果用户在对话中附带/引用了文档（文件路径、`#` 引用、粘贴的需求文本、`docs/` 下的需求文件等）→ 存在文档输入
2. 如果存在可分析的 git 改动（用户指定了分支/tag/commit，或当前分支相对主分支有 diff）→ 存在代码输入
3. 根据上述两个维度组合，确定最终输入源模式：
   - 仅文档存在 → **仅文档模式**
   - 仅代码存在 → **仅代码模式**
   - 两者都存在 → **文档 + 代码模式**（默认优先，能力最强）
4. 如果两者都无法确定（既没有文档，也没有可分析的改动），向用户询问需求来源

**三种模式的核心差异：**

- **仅文档模式**：文档描述的是"应该实现什么"，据此推演用户真实使用场景，覆盖文档中显性写出的规则和文档中隐含但必然存在的场景。
- **仅代码模式**：diff 反映的是"实际改了什么"，据此推断改动意图和影响范围。
- **文档 + 代码模式**：以文档为"预期"、代码为"现实"，重点关注两者的一致性与差异——文档要求但代码未实现的、代码实现但文档未提及的、以及两者理解不一致的地方，都是高价值测试点。

## 生成模式

根据用户的指令判断生成模式：

1. **完整模式（默认）**：同时生成冒烟测试 + 新功能完整测试，写入同一个 md 文件
2. **仅冒烟测试**：用户明确说"只生成冒烟测试"、"只要冒烟用例"时，仅生成冒烟测试部分
3. **仅新功能测试**：用户明确说"只生成新功能测试"、"只要功能测试"时，仅生成新功能完整测试部分
4. **清除测试结果**：用户说"清除测试结果"、"重置测试结果"、"清空结果"时，将指定 md 文件中所有用例的"测试结果"字段清空，但不修改用例的其他任何内容（前置条件、测试步骤、预期结果等保持不变）

当只生成单一部分时，md 文件中不需要"第一部分"/"第二部分"的标题划分，直接输出对应内容即可。

### 清除测试结果的执行规则

当用户触发清除模式时：

1. 用户必须指定目标文件（如"清除 v1.2.0.md 的测试结果"）
2. 读取指定的 md 文件
3. 将所有 `| 测试结果 | xxx |` 替换为 `| 测试结果 | |`（保留表格格式，仅清空内容）
4. 不修改文件中的任何其他内容
5. 写入文件后告知用户已清除的用例数量

## 文档来源指定

当输入源包含文档时，按以下方式获取文档内容：

- 用户在对话中直接粘贴了需求文本 → 直接使用该文本作为文档
- 用户提供了文档文件路径或通过 `#` 引用了文件（如 `.md`、`.txt`、PRD 文档、需求说明） → 读取该文件内容
- 用户说"根据 docs 里的需求文档" → 读取 `docs/` 目录下相关的需求/设计文档
- 用户提到设计稿说明、原型说明 → 读取对应说明文件
- 如果用户提到"根据文档"但未指明具体文档 → 询问用户文档的位置或让其粘贴内容

## 分支指定

- 默认使用当前 git 工作分支进行分析
- 当用户指定了某个分支名时（如"帮我生成 feature/login 分支的测试用例"），使用用户指定的分支：
  1. 执行 `git diff <主分支>..<用户指定分支> --stat` 获取该分支的文件改动列表
  2. 执行 `git diff <主分支>..<用户指定分支>` 获取完整 diff
  3. 执行 `git log <主分支>..<用户指定分支> --oneline` 获取 commit 信息
- 当用户指定了 tag 版本号时（如"帮我生成 v1.2.0 的测试用例"）：
  1. 确定上一个 tag（执行 `git describe --tags --abbrev=0 <指定tag>^` 获取前一个 tag）
  2. 执行 `git diff <上一个tag>..<指定tag> --stat` 获取两个 tag 之间的文件改动列表
  3. 执行 `git diff <上一个tag>..<指定tag>` 获取完整 diff
  4. 执行 `git log <上一个tag>..<指定tag> --oneline` 获取 commit 信息
  5. 如果找不到上一个 tag，则使用主分支作为对比基准
- 当用户指定了 commit hash 时（如"帮我生成 ec0eabb 这个提交的测试用例"）：
  1. 执行 `git diff <commit hash>^..<commit hash> --stat` 获取该提交的文件改动列表（单个提交与其父提交对比）
  2. 执行 `git diff <commit hash>^..<commit hash>` 获取完整 diff
  3. 执行 `git log <commit hash> -1 --oneline` 获取该提交的信息
  4. 如果用户提供的是一段 commit 范围（如"从 abc123 到 def456"），则使用 `git diff <起始commit>..<结束commit>` 获取范围内的改动
- 不需要切换分支，直接通过 git diff 远程比较即可

## 工作流程

### 第一步：判定输入源并检查 test-cases 目录

1. 按"输入源判定"章节确定本次的输入源模式（仅文档 / 仅代码 / 文档 + 代码），后续步骤依此分支
2. 检查当前项目根目录下是否存在 `test-cases` 文件夹
3. 如果不存在，自动创建 `test-cases` 文件夹
4. 如果已存在，读取其中已有的测试用例文件，了解历史测试覆盖范围

### 第二步：按输入源获取分析素材

根据第一步判定的输入源，执行对应的素材获取步骤。

#### 2A. 获取文档内容（仅文档模式、文档 + 代码模式）

1. 按"文档来源指定"章节的方式定位并读取文档内容
2. 通读全文，提取以下结构化信息：
   - **功能清单**：文档描述了哪些功能点 / 需求条目
   - **业务规则**：每个功能的具体规则、约束、计算逻辑、状态流转
   - **输入与输出**：字段、参数、取值范围、格式要求、默认值
   - **角色与权限**：不同用户角色的可见性和操作权限差异
   - **异常与提示**：文档中描述的报错、提示文案、失败处理
   - **验收标准**：文档中明确写出的"完成定义 / 验收条件"（如有）
3. 标记文档中**含糊、缺失或自相矛盾**的地方，这些是测试时需要重点确认的风险点

#### 2B. 获取代码改动（仅代码模式、文档 + 代码模式）

1. 确定目标分支：
   - 如果用户指定了分支名，使用用户指定的分支作为目标分支
   - 如果用户未指定，执行 `git branch --show-current` 获取当前分支名作为目标分支
2. 确定主分支名（通常为 `main` 或 `master`）：优先执行 `git symbolic-ref refs/remotes/origin/HEAD` 获取（跨平台通用）；若不可用，再从 `git remote show origin` 的输出中查找 `HEAD branch`（Windows PowerShell 下用 `Select-String 'HEAD branch'` 代替 `grep`）
3. 执行 `git diff <主分支>..<目标分支> --stat` 获取目标分支相对于主分支修改的所有文件列表
4. 执行 `git diff <主分支>..<目标分支>` 获取完整的代码差异内容
5. 执行 `git log <主分支>..<目标分支> --oneline` 获取目标分支的所有 commit 信息

### 第三步：分析并建立测试基准

根据输入源分析素材，形成测试用例的生成依据。

#### 3A. 分析代码改动（涉及代码时）

根据 diff 内容，分析以下信息：

1. **新增功能**：新增的组件、页面、接口、交互逻辑
2. **修改功能**：对已有功能的修改（bug 修复、逻辑调整、UI 变更）
3. **涉及模块**：变更涉及哪些业务模块
4. **影响范围**：变更可能影响的关联功能（用于冒烟测试范围判定）

#### 3B. 分析文档需求（涉及文档时）

根据 2A 提取的信息，梳理出：

1. **待测功能点**：文档中每个需要验证的功能 / 需求条目
2. **业务规则矩阵**：把规则拆解为可验证的条件组合（不同输入 → 不同预期结果）
3. **场景推演**：站在真实用户角度，推演文档隐含但未写明的使用场景（如正常流程之外的中断、回退、并发、多次操作等）

#### 3C. 文档与代码交叉比对（文档 + 代码模式专属）

以文档为"预期需求"、代码为"实现事实"，重点识别三类高价值测试点：

1. **一致性验证**：文档要求且代码已实现的功能，验证实现是否符合文档规则
2. **文档要求但代码疑似未实现 / 实现不全**：作为重点测试点，用例中标注"需确认是否遗漏"
3. **代码实现但文档未提及**：可能是额外改动或隐藏逻辑，作为探索性测试点，用例中标注"文档未覆盖，需确认"

当文档描述与代码实现产生冲突时，不擅自认定谁对谁错，而是生成用例把冲突点暴露出来，交由测试执行时确认。

**辅助理解项目背景（所有模式通用）：**

无论哪种输入源，为了确保用例贴合实际业务，应额外读取以下内容辅助理解：

1. 项目根目录的 `.kiro/steering/` 目录下的 md 文件（如果存在，优先读取，这是项目的核心说明文档）
2. 项目根目录的 `README.md`（了解项目整体功能和架构）
3. `docs/` 目录下的需求文档或设计文档（如果存在，且未作为主输入文档）
4. 相关模块的现有代码（了解完整业务逻辑）
5. 相关组件的注释和 props 定义（理解组件用途和交互方式）

这些信息用于确保生成的测试用例贴合实际业务场景，而非仅基于文档字面或代码字面意思。

### 第四步：确定测试用例文件

**判断逻辑：**

1. **用户指定了文件**：如果用户明确指定了要写入的 md 文件（如"把用例写到 v1.2.0.md 里"、"在 test-cases/v1.2.0.md 中补充"），则必须只在该文件中填充测试用例，不创建新文件
   - 如果指定文件已存在，在文件末尾追加新生成的用例内容（保留已有内容不动）
   - 如果指定文件不存在，在 `test-cases` 目录下创建该文件
2. **用户未指定文件**：自动确定文件名，按以下优先级：
   - 从分支名提取版本号作为文件名（如 `release/v1.2.0` → `v1.2.0.md`）
   - 从 `package.json` 的 `version` 字段获取版本号作为文件名
   - 使用分支名作为文件名（如 `feature/login` → `feature-login.md`）
   - **仅文档模式**（无分支信息时）：从文档标题或需求名提取文件名（如需求文档标题为"用户登录优化" → `user-login.md` 或 `用户登录优化.md`）
   - 如果以上均无法确定，询问用户

在 `test-cases` 目录下创建或写入对应的 md 文件，内容结构如下：

#### 文件格式模板

> 模板标题按输入源填写：仅代码 / 文档+代码模式用版本号（如 `v1.2.0 测试用例`）；仅文档模式用需求名（如 `用户登录优化 测试用例`）。下方 `<版本号 / 需求名>` 占位符按实际情况替换。

```markdown
# <版本号 / 需求名> 测试用例

> 测试对象：<版本号 / 需求名>
> 测试范围：<新功能/需求点列表>（新功能完整测试）+ <冒烟测试模块列表>（基本功能冒烟测试）

---

## 一、<功能名>

| 项目 | 内容 |
|------|------|
| 前置条件 | <执行该用例前需要满足的条件> |
| 测试步骤 | <编号的操作步骤> |
| 预期结果 | <预期的正确表现> |
| 测试结果 | |

...更多用例...

---

## 第二部分：基本功能冒烟测试

## N、<模块名>
```

### 第五步：生成新功能完整测试用例（第一部分）

**核心心态：以测试工程师的视角思考，而非文档 / 代码的复述者**

生成用例时，不要只是把文档描述或代码逻辑逐条翻译成用例。要带着一名资深测试工程师的批判性思维和经验主动挖掘风险点：

- **不轻信"正常"**：文档写"用户输入手机号"，测试要想到——空号、非法格式、超长、含空格、国际号码、重复提交会怎样？
- **关注状态与流程**：功能在不同前置状态下表现是否一致？中途退出、返回、刷新、断网重连后数据是否正确？重复操作、并发操作会不会出问题？
- **质疑一致性**：文档、UI 文案、实际交互、错误提示之间是否统一？多端 / 多语言下是否一致？
- **推演真实用户行为**：用户不会只按理想路径操作，要覆盖误操作、乱序操作、边界时间点（如临界时间、跨天、活动开始/结束瞬间）等。
- **主动补文档 / 代码没写的场景**：显性需求只是起点，隐含的异常分支、兼容性、数据边界、权限组合往往才是缺陷高发区。这些即使文档和代码都没提，也要作为测试点提出。
- **风险优先级排序**：核心业务、涉及金额 / 数据 / 权限的功能要投入更多用例密度；纯展示类可适当精简。

针对每个功能点，至少从以下维度设计用例：

1. **正常路径测试**：功能的核心正向流程
2. **边界条件测试**：极端值、空值、最大最小值、超长、临界点等
3. **异常场景测试**：网络异常、数据异常、权限不足、非法输入、并发 / 重复操作等
4. **状态与流程测试**：不同前置状态、中断恢复、回退、刷新、重复进入等
5. **多端适配测试**：如项目涉及 PC 端和移动端，需分别测试
6. **多语言测试**：如项目涉及国际化，需测试多语言显示
7. **交互细节测试**：动画、状态切换、按钮可用性、加载态、空态等

**用例编写原则：**
- 每个用例必须有明确的前置条件
- 测试步骤必须具体、可操作，使用编号列出
- 预期结果必须明确、可验证；预期结果应来自"需求应有的正确表现"，而非简单照抄代码当前行为（代码本身可能有 bug）
- 测试结果字段留空，让用户手动填写
- 用例要覆盖本次输入源的所有内容，不遗漏：
  - 仅文档模式：覆盖文档所有功能点及其隐含场景
  - 仅代码模式：覆盖当前分支的所有代码改动
  - 文档 + 代码模式：覆盖文档需求 + 代码改动，并额外为第三步 3C 识别出的文档/代码不一致点单独生成用例
- 对于文档模糊、缺失或与代码冲突的地方，生成用例把风险点显式暴露出来，并在用例中标注"需确认"

### 第六步：生成冒烟测试用例（第二部分）

冒烟测试用于验证已有核心功能在本次需求 / 改动上线后仍正常工作：

1. 读取 `test-cases` 目录中已有的历史测试用例文件
2. 结合当前项目代码（如有代码仓库可读），识别核心业务模块；无代码时见下方"仅文档模式的降级处理"
3. 判定本次需求 / 改动的影响范围，选择可能被影响的已有功能模块：
   - 仅代码模式：根据 diff 的影响范围判定
   - 仅文档模式：根据文档所述功能在系统中的位置，推断可能关联 / 影响的既有模块
   - 文档 + 代码模式：结合文档影响范围与代码改动影响范围综合判定
4. 为每个模块生成 1-3 个核心路径的冒烟用例（只验证主流程通不通）
5. 如果是首次生成（无历史用例），则根据项目代码中的主要功能模块生成冒烟用例

**冒烟测试选择原则：**
- 优先选择与本次需求 / 改动有依赖或关联关系的模块
- 每个模块只测核心流程，不测边界场景
- 如果某模块在本次完整测试中已覆盖，冒烟测试可简化或跳过该模块

**仅文档模式的降级处理：**
当运行环境没有代码仓库可读（如纯 PRD 评审阶段），无法通过代码识别既有模块时：
- 仅依据历史用例文件（如有）和文档中提及的关联功能，推断需要冒烟验证的模块
- 若既无代码也无历史用例，则跳过冒烟测试，只输出新功能完整测试，并在摘要中说明"因缺少代码 / 历史用例，未生成冒烟测试"

### 第七步：直接写入文件并输出摘要

1. 将生成的测试用例直接写入 md 文件，无需等待用户确认
2. 输出变更摘要：
   - 生成的文件路径
   - 新功能测试用例数量（如有）
   - 冒烟测试用例数量（如有）
   - 覆盖的模块列表

## 注意事项

- 用例编号规则：`TC-<模块序号>.<用例序号>`，如 `TC-1.1`、`TC-2.3`
- 每个用例的"测试结果"字段必须留空（`| 测试结果 | |`），由用户手动填写
- 用例内容要基于实际的需求文档和 / 或代码改动，不要凭空臆造不存在的功能；但可以基于需求合理推演隐含场景（这与臆造功能不同）
- 如果 diff 或文档内容过大无法一次分析完，分模块 / 分需求点逐步分析
- 测试用例要考虑项目的实际技术栈（Web/移动端/桌面端等）
- 如果项目有多端适配（PC + Mobile），相关功能需要分端编写用例
- 如果项目有国际化（i18n），需要包含多语言相关的用例
- 冒烟测试排在文件后面（第二部分），新功能完整测试排在前面（第一部分）
- 模块序号在整个文件中连续递增（冒烟测试从一开始，新功能接续编号）

## 排除非业务文件（涉及代码分析时）

分析 diff 时（仅代码模式、文档 + 代码模式），以下类型的文件改动不需要生成测试用例（除非改动涉及业务展示逻辑）：

- `package.json` / `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` 的依赖更新
- `.gitignore`、`.eslintrc`、`.prettierrc`、`tsconfig.json` 等配置文件
- 纯图片资源替换（`.png`、`.jpg`、`.svg` 等，除非涉及展示逻辑变更）
- `README.md`、`CHANGELOG.md` 等文档文件的改动（注意：这里指 diff 中被修改的文档文件；如果用户把某个文档作为需求输入源，则另当别论，按文档模式处理）
- 测试用例文件自身（`test-cases/` 目录下的文件）
- 构建脚本、CI/CD 配置（如 `.github/workflows/`、`Dockerfile` 等）

仅针对业务代码的改动（组件、页面、接口、状态管理、工具函数等）生成测试用例。

## 追加模式的编号衔接

当向已有 md 文件追加用例时：

1. 先读取已有文件内容，找到当前最大的模块序号和用例序号
2. 新增用例的编号从已有最大编号之后开始递增
3. 例如已有文件最后一个模块是"五"（TC-5.x），新追加的模块从"六"开始（TC-6.1）
4. 不能出现编号重复或跳跃的情况

## 用户指定测试重点

当用户明确指定了某些模块或功能为测试重点时（如"重点测登录"、"充值多写几个用例"）：

1. 对指定重点模块生成更全面的用例，覆盖更多边界条件和异常场景
2. 非重点模块仍按正常密度生成用例，确保基本覆盖
3. 在文件头部的"测试范围"描述中标注重点测试模块

## 用例覆盖度自检

测试用例写入完成后，自动进行覆盖度自检。自检的比对基准取决于输入源：

- **仅代码模式**：将 diff 涉及的业务文件 / 改动点列表与生成的用例进行对比
- **仅文档模式**：将文档中提取的功能点 / 需求条目列表与生成的用例进行对比
- **文档 + 代码模式**：将文档功能点 + 代码改动点合并列表与生成的用例进行对比，并额外确认第三步 3C 识别出的文档/代码不一致点是否都有用例覆盖

自检步骤：

1. 建立"待覆盖清单"（按上述输入源确定）
2. 逐一确认每个待覆盖项（新增功能、修改接口、UI 变更、文档需求条目、业务规则、文档/代码不一致点等）是否有对应的测试用例覆盖
3. 如果发现存在未覆盖项，在输出摘要中列出，例如：

```
⚠️ 以下内容未生成对应测试用例，请确认是否需要补充：
- 【代码】src/components/NewBanner.vue（新增组件，未生成展示类用例）
- 【代码】src/api/payment.js（接口参数变更，未生成参数校验用例）
- 【文档】需求 3.2 "优惠券叠加规则"（业务规则未拆解为用例）
- 【差异】文档要求短信验证码 60s 倒计时，代码未见相关实现（需确认是否遗漏）
```

4. 说明未覆盖的原因（如纯样式调整无需功能测试、内部重构不影响外部行为、文档章节为非功能性说明等）
5. 如果所有待覆盖项均已覆盖，输出"✅ 所有需求 / 改动点均已覆盖"
