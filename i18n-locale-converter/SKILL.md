# i18n 语言包转换与写入

## 触发场景

当用户提供了一段不规则格式的多语言翻译内容（可能来自翻译文档、Excel 复制、PM 提供的文本等），需要将其转换为项目中语言包文件的格式并写入对应文件时，使用此 skill。

## 工作流程

### 第一步：定位项目语言包

1. 在当前项目中查找语言包目录，常见位置：
   - `src/langs/`
   - `src/locales/`
   - `src/i18n/`
   - `src/lang/`
   - `src/language/`
2. 读取语言包入口文件（如 `index.js`、`index.ts`），确定支持的语种列表
3. 读取各语种文件，了解现有的 key 命名规范和文件格式

### 第一步 B：分析语言包存储位置（关键步骤）

语言包内容不一定全部存储在独立的语言包文件（JSON/JS）中，可能分散在项目代码里。必须先分析每条翻译内容应该写入的**正确位置**：

**常见的语言包存储模式：**

1. **独立语言包文件**：内容集中在 `locale/*.json` 或 `langs/*.js` 等文件中，通过 `vue-i18n` 的 `$t()` 调用
2. **代码内 switch/computed**：内容以 `switch(lang)` 或 computed 属性的形式写在 `.vue` 组件中（如 App.vue 的 metaInfo、SEO 信息等）
3. **混合模式**：部分内容在语言包文件中，部分内容在代码中

**分析步骤：**

1. **读取主组件文件**（如 `App.vue`、`Home.vue`）中是否存在按语言切换的逻辑（switch-case、对象映射、computed 等）
2. **对照用户提供的翻译内容**，判断每条内容应该写入哪里：
   - 如果对应的 key 或文案已存在于某个 `.vue` 文件的 switch-case/computed 中 → 修改该 `.vue` 文件对应位置
   - 如果对应的 key 已存在于语言包 JSON/JS 文件中 → 修改语言包文件
   - 如果是全新内容，参考项目现有模式决定放哪里
3. **绝不能将代码中的语言切换逻辑内容错误地写入语言包文件**，反之亦然
4. 如果项目是混合模式（如 footer 文案在 JSON 中、SEO meta 在 App.vue computed 中），必须分别处理，将内容写到各自正确的位置

**输出确认（写入前）：**
```
📍 语言包存储位置分析：
- footer 相关（copyright/privacy/terms/owner）→ src/locale/*.json
- SEO 相关（title/description/keywords）→ src/App.vue computed 属性
```

### 第二步：分析现有命名规范

通过阅读现有语言包文件，总结 key 的命名规则：

- **命名风格**：观察是驼峰（camelCase）、下划线（snake_case）还是其他
- **前缀规则**：观察是否有模块前缀（如 `module1`、`rechargeEvent`、`puzzleEvent`）
- **层级规则**：观察 key 是扁平的还是嵌套的对象
- **编号规则**：观察相似 key 的编号方式（如 `Day1Title`、`Day2Title`）
- **后缀规则**：观察功能性后缀（如 `Title`、`Tip`、`Btn`、`Rule`、`Record`）

### 第三步：解析用户提供的内容

用户提供的不规则内容可能是以下形式：

- 表格形式（中文 | 英文 | 法文 ...）
- 换行分隔的多语言文本
- JSON/对象形式但 key 不规范
- 纯文本列表
- Excel/文档复制的内容
- 带有序号或标记的翻译内容

**内容通常有一定规律，必须先分析规律再操作：**

1. **识别排列规律**：用户提供的内容通常按固定的语种顺序排列（如每行依次是：英文、德语、法语、西语、葡语），需要先观察前几条内容，确认各语种的排列顺序和分隔方式
2. **确认语种对应关系**：根据识别出的规律，将每一条翻译内容正确归类到对应语种
3. **识别分隔符**：观察内容是用 Tab、空格、换行、竖线还是其他符号分隔各语种
4. **验证规律一致性**：检查整段内容是否始终遵循同一排列规律，如果中间有不一致的地方，先向用户确认

完成语种区分后，再进行以下判断：
1. 每条文本的业务含义（用于生成合适的 key 名）
2. 是新增内容还是替换现有内容

### 第四步：生成规范的 key 名称

根据第二步总结的命名规范，为新内容生成 key 名称：

1. **确定模块前缀**：根据内容所属功能模块，使用对应的前缀
2. **确定语义后缀**：根据文本用途（标题、按钮、提示、规则等）添加后缀
3. **保持一致性**：新 key 的风格必须与项目已有 key 完全一致
4. 如果用户指定了 key 名或前缀，优先使用用户指定的

### 第五步：写入语言包文件

1. **替换模式**：如果用户说"替换"，找到对应 key 并**仅更新其值**，不得修改或删除其他无关的 key
2. **补充模式**：如果用户说"补充/新增"，按照以下规则插入新的 key-value：
   - 新增的 key 必须按照已有语言包的命名习惯命名（前缀、后缀、编号方式保持一致）
   - 新增的 key 必须插入到同一模块的相同位置（如紧跟在同前缀的其他 key 之后），不能随意放在文件末尾
   - 所有语种文件中新增 key 的位置要保持一致
3. **仅修改用户提供翻译的语种**：只写入用户明确给出了翻译内容的语种文件/代码位置，未提供翻译的语种文件完全不碰
4. **保持格式**：写入时保持与原文件一致的代码风格（引号、缩号、逗号等）
5. **精准定位**：当用户指定替换或补充某个模块/部分的语言包时，必须先分析已有语言包内容，精准定位到对应部分，只修改用户指定的那部分内容，其余部分完全不动

**多语种并行写入：**

当涉及多个语种文件需要修改时，将内容分析归类到各语种后，每个语种启动一个独立的子任务同时进行写入操作：

1. 内容分析归类完成后，为每个语种文件创建一个子任务
2. 所有语种的子任务并行执行（同时写入各语种文件）
3. 每完成一个语种文件的写入，更新任务进度（如"已完成 3/8 语种文件写入"）
4. 所有子任务完成后，汇总结果进入校验步骤

## 数据保护规则（严格遵守）

1. **禁止主动删除**：除非用户明确要求"删除某个 key"或"移除某段内容"，否则绝不能删除已有的任何语言包数据（包括 key、value、注释）
2. **最小变更原则**：每次操作只修改用户明确要求的部分，不做额外的"清理"或"优化"
3. **保留未提及的内容**：用户提供的翻译内容中如果没有涵盖某些已有的 key，这些 key 必须原封不动保留
4. **数组部分替换**：如果用户只提供了数组中部分元素的更新，只替换对应元素，不删除数组中的其他元素
5. **确认删除操作**：如果分析后发现需要删除某些 key 才能完成用户的需求，必须先列出将被删除的 key 并征得用户确认
6. **模块隔离**：当用户指明是某个部分或某个模块的语言包内容时，操作范围严格限定在该模块内（如用户说"拼图相关"则只能修改 `puzzleEvent` 前缀的 key），绝不能误修改到其他模块的内容。如果用户提供的内容中某些文案与其他模块已有的 key 文案相似（如多个模块都有 "Event Rules"），必须根据用户指定的模块范围来判断应修改哪个 key，不能跨模块替换
7. **未提供语种绝不修改（最高优先级）**：
   - 只能修改用户**明确提供了翻译内容**的语种文件
   - 如果用户只提供了英语、俄语、阿语三种翻译，则只能修改 en、ru、ar 对应的文件/代码，绝不能碰 de、fr、es、pt 等用户未提供翻译的语种
   - 即使发现其他语种文件中有明显错误（如 es 和 pt 的值互换），也不能主动修正，除非用户明确提供了该语种的正确值
   - 不得为未提供翻译的语种使用英文或任何其他语言做兜底填充
   - 新增 key 时，如果用户没有提供某个语种的翻译，该语种文件中不添加这个 key（宁缺毋错）
   - 在摘要中列出用户未覆盖的语种，提醒用户后续补充，但绝不代替用户做填充操作

## 输出要求

1. 列出将要操作的文件路径
2. 列出生成的 key 名称及其对应的各语种内容
3. 直接并行启动多个子代理进行各语种文件的写入，不等待用户确认
4. 写入过程中必须输出每个语种的详细任务进度，包括语种级别进度和单个语种内部的操作进度，格式如：
   ```
   📝 [1/8] 英语（en）开始写入...
     - 定位插入位置 ✅
     - 写入 key: moduleTitle ✅
     - 写入 key: moduleBtn ✅
     - 写入 key: moduleRule1 ✅
   ✅ [1/8] 英语（en）写入完成（共 3 个 key）

   📝 [2/8] 德语（de）开始写入...
     - 定位插入位置 ✅
     - 写入 key: moduleTitle ✅
     - 写入 key: moduleBtn ✅
     - 写入 key: moduleRule1 ✅
   ✅ [2/8] 德语（de）写入完成（共 3 个 key）

   ...

   ✅ [8/8] 全部语种写入完成
   ```
5. 全部写入完成后展示变更摘要
5. **写入后校验**：所有语种文件修改完成后，必须重新读取每个修改过的文件，检查以下内容：
   - 修改/新增的 key 和 value 是否正确写入
   - 是否有误删除已有内容
   - 各语种之间的 key 是否对齐一致（不能出现某个语种漏改的情况）
   - 文件语法是否正确（引号闭合、逗号、括号等）
   - key 的排列顺序是否与预期位置一致（新增的 key 是否插入到了同模块、同前缀的正确位置，而非文件末尾或其他无关位置）
   - 如果发现问题，立即修复并告知用户
6. **修改内容摘要**：校验通过后，生成一份方便阅读的修改内容摘要，格式如下：

   ```
   ## 📝 修改内容摘要

   **操作类型**：新增 / 替换 / 混合
   **涉及文件**：
   - `src/langs/en.js`
   - `src/langs/zh.js`
   - ...

   **修改明细**：

   | Key | 操作 | EN | ZH | ... |
   |-----|------|----|----|-----|
   | moduleTitle | 新增 | Module Title | 模块标题 | ... |
   | moduleBtn | 替换 | Click Here | 点击这里 | ... |

   **统计**：共修改 X 个文件，新增 N 个 key，替换 M 个 key
   ```

   摘要要求：
   - 使用表格展示每个 key 的操作类型和各语种内容，方便一目了然地核对
   - 如果 value 内容过长（超过 30 字符），截断并加 `...` 后缀
   - 底部附上统计信息（文件数、新增数、替换数）
   - 如果本次修改涉及多个模块（通过 key 前缀或用户指定的模块划分），需要按模块分别列出摘要表格，格式如下：

   ```
   ### 模块：rechargeEvent

   | Key | 操作 | EN | ZH | ... |
   |-----|------|----|----|-----|
   | rechargeEventTitle | 新增 | Recharge | 充值 | ... |
   | rechargeEventBtn | 替换 | Go | 前往 | ... |

   ### 模块：puzzleEvent

   | Key | 操作 | EN | ZH | ... |
   |-----|------|----|----|-----|
   | puzzleEventRule1 | 新增 | Rule 1 | 规则一 | ... |
   ```

## 语种缺失检测

写入完成后，检查用户提供的翻译内容是否覆盖了项目支持的所有语种：

1. 对比项目语种列表与用户提供的翻译语种
2. 如果存在缺失语种（如项目支持 7 种语言但用户只给了 3 种），在摘要中明确列出未覆盖的语种
3. **绝不为缺失语种做任何兜底填充**，只提醒用户后续补充

摘要中的展示格式：
```
⚠️ 以下语种用户未提供翻译，相关文件未做任何修改：
- 德语（de）
- 法语（fr）
- 葡语（pt）
- 西语（es）
请后续提供这些语种的翻译后再操作。
```

## 重复 key 冲突检测

在写入前（第四步生成 key 之后），检查新生成的 key 是否与已有 key 重名：

1. 遍历所有语种文件，检查新 key 是否已存在
2. 如果发现重名：
   - 若用户意图是"替换"，则正常执行替换
   - 若用户意图是"新增/补充"，则提示用户该 key 已存在，询问是要覆盖已有值还是使用另一个 key 名
3. 避免无意中覆盖已有翻译内容

## 特殊字符转义预览

当用户提供的文本中包含以下特殊字符时，在写入前输出转义后的结果供用户查看：

- 单引号 `'` / 双引号 `"` — 根据文件使用的引号风格进行转义
- 换行符 — 转义为 `\n`
- HTML 标签（如 `<br>`、`<span>` 等）— 保持原样但提示用户注意
- 模板变量（如 `{0}`、`${name}`、`%s`）— 高亮提示，确保各语种模板变量一致

输出格式：
```
⚠️ 以下 key 包含特殊字符，已自动转义处理：
- moduleRule1: "You\'ve earned {0} points" （含转义引号和模板变量）
- moduleDesc: "Line 1\nLine 2" （含换行符）
```

## 注意事项

- 值为数组的 key（如规则列表、概率列表），保持数组格式
- 如果文本中包含特殊字符（引号、换行等），需要正确转义
- URL 类的值各语种可能不同（如不同语种的隐私政策链接），需要注意区分
- `lang` 字段是语种标识，不要修改
- 保持文件末尾的 `export default languages` 或类似导出语句不变
- 如果项目使用 TypeScript，注意类型定义的兼容性
- **占位符识别**：当内容中出现单个 `X` 或多个 `X`（如 `XXXX`、`XXXXX`）、`202X/X/X` 等明显为占位符的文本时，判断其是否为待填充的占位内容。如果确认是占位符（表示具体数值/日期/时间等尚未确定），则不将该部分写入语言包文件，跳过该条目或保留语言包中已有的值不变
