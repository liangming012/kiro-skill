# 设计稿图片资源集成与验证

## 触发场景

当满足以下**全部**条件时触发此 skill：

1. 当前项目是前端项目（Vue 2、Vue 3、React、纯 HTML/CSS、Next.js、Nuxt 等）
2. 用户需求涉及设计稿相关内容（PSD、PSB、设计稿、切图、视觉还原等）

具体包括但不限于：
- 用户要求根据设计稿实现/修改页面
- 用户提供了 PSD/PSB 文件并要求将其中的素材用到项目中
- 用户要求替换项目中的图片为设计稿中的新版本
- 用户要求新增设计稿中的图片元素到项目中
- 用户要求对比当前页面与设计稿的差异并修正

## 核心原则

1. **先分析后执行**：必须先完成需求分析和图片清单整理，再开始导出操作
2. **区分新增与替换**：每张图片必须明确标记是新增还是替换，替换需额外分析原图信息
3. **图片图层去重**：导出任何图片（包括普通图片和背景图）时，都必须检查并隐藏该图片图层组内代码中已独立渲染的元素图层，绝不允许导出的图片中出现与代码重复的内容
4. **严格限定修改范围**：当用户指定了只修改某个模块或某个功能时，操作范围严格限定在该模块/功能内，不触碰其他无关内容
5. **调用已有 skill 和工具**：图片导出使用 `list-layers` skill（读取图层）和 `ps-export` skill（导出 PNG），图片尺寸设置使用 `image-sizing-guide` skill，图像处理/裁切/合成使用 Pillow（通过 design-to-code 的虚拟环境调用）
6. **验证驱动**：所有图片处理完成后必须通过 Playwright 截图验证，确保与设计稿一致
7. **失败重试有上限**：同一图片最大重试 5 次，超过则标记失败
8. **多任务并行**：当有多个独立任务可以同时进行时（如多张图片导出、多个语种图片处理、多个文件写入），启动多个子任务并行操作，提高执行效率

### 第一步：Python 环境检测与虚拟环境初始化

**确认系统 Python 可用且虚拟环境已就绪，后续所有涉及 Python 的操作（第五步 Pillow 获取图片尺寸、第七步导出后处理、第八步格式转换、第九步 Playwright 截图等）都依赖本步骤。**

#### 1.1 检测系统 Python 是否可用

**检测策略**：直接输出系统环境变量和用户环境变量中 PATH 的完整内容，由 AI 分析其中是否包含 Python 相关路径（如 `Python311`、`Python39`、`python37`、`Anaconda3`、`miniconda3`、`pyenv` 等）。不做硬编码匹配，因为 Python 安装目录名可能有多种形式。

**Windows 检测命令**：

```powershell
# 输出系统级 PATH（Machine）和用户级 PATH（User）的所有目录，供 AI 分析
Write-Host "=== 系统环境变量 PATH (Machine) ==="
([System.Environment]::GetEnvironmentVariable("Path", [System.EnvironmentVariableTarget]::Machine)) -split ";" | ForEach-Object { if ($_.Trim()) { Write-Host $_ } }
Write-Host ""
Write-Host "=== 用户环境变量 PATH (User) ==="
([System.Environment]::GetEnvironmentVariable("Path", [System.EnvironmentVariableTarget]::User)) -split ";" | ForEach-Object { if ($_.Trim()) { Write-Host $_ } }
```

**AI 分析规则**：

从输出的所有路径中，识别包含 Python 的目录。常见模式包括但不限于：

| 路径模式 | 说明 |
|----------|------|
| `*\Python3*\` | 官方安装（如 `C:\Python311\`、`C:\Python39\`） |
| `*\Python\Python3*\` | 官方安装默认路径（如 `C:\Users\xxx\AppData\Local\Programs\Python\Python311\`） |
| `*\python*\` | 小写变体 |
| `*\Anaconda3*\` | Anaconda 环境 |
| `*\miniconda3*\` | Miniconda 环境 |
| `*\pyenv\*\` | pyenv-win 管理的版本 |
| `*\scoop\apps\python*\` | Scoop 安装 |
| `*\WindowsApps\*` | Microsoft Store 安装的 Python |

**找到疑似 Python 目录后**，执行验证：

```powershell
# 用找到的目录验证 Python 是否可用（将 <找到的目录> 替换为实际路径）
& "<找到的目录>\python.exe" --version
```

如果从 PATH 目录中找不到任何 Python 相关路径，再检查 py launcher：

```powershell
# 兜底：检查 Windows Python Launcher
if (Test-Path (Join-Path $env:SystemRoot "py.exe")) { & py --version } else { Write-Host "py launcher 也不存在" }
```

**macOS/Linux 检测命令**：

```bash
# 输出 PATH 中的所有目录，供 AI 分析
echo "=== 环境变量 PATH ==="
echo "$PATH" | tr ':' '\n'
```

**AI 分析后的操作**：

1. 从输出中识别出包含 Python 可执行文件的目录路径
2. 用该路径下的 `python.exe`（Windows）或 `python3`/`python`（macOS/Linux）执行 `--version` 验证
3. 确认版本 ≥ 3.8 后，将完整路径记录为 `$pythonCmd`，供后续步骤使用
4. 如果分析所有路径后确认无 Python → 中断流程并提示用户安装

**如果系统未安装 Python**：

立即中断流程，向用户提示以下安装方式并等待用户确认安装完成后再继续：

| 操作系统 | 推荐安装方式 | 命令 |
|----------|-------------|------|
| Windows | Python 官网安装包 | 访问 https://www.python.org/downloads/ 下载安装，安装时勾选 "Add Python to PATH" |
| Windows | winget | `winget install Python.Python.3.11` |
| Windows | scoop | `scoop install python` |
| macOS | Homebrew | `brew install python@3.11` |
| macOS | 官网安装包 | 访问 https://www.python.org/downloads/ |
| Linux (Debian/Ubuntu) | apt | `sudo apt update && sudo apt install python3 python3-venv python3-pip` |
| Linux (CentOS/RHEL) | dnf | `sudo dnf install python3 python3-pip` |

**要求**：
- Python 版本 ≥ 3.8
- 安装后 `python`（或 `python3`）命令必须在 PATH 中可用
- Windows 用户安装时**必须勾选 "Add Python to PATH"**，否则后续命令无法找到 Python

### 第二步：分析用户需求与项目现状

1. **确认前端项目类型**：
   - 查看 `package.json`、框架配置文件，确认项目类型（Vue 2/3、React、纯 HTML 等）
   - 确认项目的静态资源目录结构（如 `src/assets/`、`public/images/`、`static/` 等）

2. **判断端类型（PC 端 / 移动端）**：

   **必须在第二步确认端类型，后续所有尺寸计算和验证都依赖此判断。**

   通过设计稿画布宽度判断：
   
   | 设计稿画布宽度 | 端类型 | Playwright 视口 | CSS 单位 |
   |---------------|--------|----------------|----------|
   | **750px** | 移动端（WAP） | 750 × 1334 | rem（像素值 ÷ 100） |
   | **1920px** | PC 端 | 1920 × 1080 | px（像素值直接使用） |
   | 其他宽度 | 需结合项目代码判断 | 按实际确认的端类型设置 | 按实际确认的端类型设置 |
   
   判断优先级：
   1. **设计稿画布宽度**（最优先）：读取 PSD/PSB 图层结构时获取的 `canvas_size` 宽度值
      - 宽度 = 750 → 移动端
      - 宽度 = 1920 → PC 端
      - 宽度为其他值（如 1440、828、1080 等）→ 结合项目代码进一步判断，若无法确认则询问用户
   2. **项目目录/文件名线索**（辅助确认）：
      - 路径包含 `wap`、`mobile`、`m-`、`h5` → 移动端
      - 路径包含 `pc`、`desktop`、`web` → PC 端
   3. **项目代码中已有的单位**（辅助确认）：
      - 样式中大量使用 rem 且符合 ÷100 规律 → 移动端
      - 样式中使用 px → PC 端
   4. **无法判断时**：默认 PC 端

   确认后在后续步骤中标注：`📱 移动端项目（设计稿 750px）` 或 `🖥️ PC 端项目（设计稿 1920px）`

3. **分析用户需求并确定修改范围**：
   - 理解用户要实现/修改的功能或页面
   - 确认涉及哪些组件/页面文件
   - 读取相关代码文件，了解当前的图片引用方式和路径
   - **确定修改范围边界**：
     - 如果用户指定了具体模块（如"只改头部区域"、"只处理奖品模块"、"只修改登录页"），则后续所有操作**严格限定在该模块范围内**
     - 如果用户指定了具体功能（如"只替换按钮图片"、"只处理背景图"），则只处理该功能相关的图片
     - 设计稿中属于其他模块/功能的内容**一律不动**，即使发现存在差异也不主动修改
     - 在清单整理时只列出范围内的图片，不列出范围外的图片
   
   **范围限定标注**：确认范围后在后续步骤中标注，如：
   - `🎯 修改范围：头部区域（Header Section）`
   - `🎯 修改范围：奖品模块（Prize Module）相关图片`
   - `🎯 修改范围：全页面（用户未限定范围）`

   **超出范围时的处理**：
   - 如果在分析过程中发现范围外的内容也存在明显问题（如图片缺失、尺寸错误），不主动修复，但在最终摘要报告中以「建议事项」的形式告知用户
   - 绝不因为"顺手"而修改范围外的文件或图片

4. **确认设计稿文件**：

   按以下优先级定位设计稿文件：
   
   1. **用户明确指定**：如果用户提供了 PSD/PSB 文件路径，直接使用
   2. **自动查找项目 design 目录**：如果用户未指定路径，优先在项目根目录下查找 `design/` 目录：
      ```powershell
   # 查找项目根目录下的 design 目录中的 PSD/PSB 文件
   Get-ChildItem -Path ./design -Recurse -Depth 2 -Include *.psd,*.psb 2>$null
   ```
      - 如果找到 PSD/PSB 文件，列出文件列表供确认（如果只有一个则直接使用）
      - 如果 `design/` 目录存在但没有 PSD/PSB 文件，告知用户目录为空
      - 也检查其他常见设计稿目录名：`design/`、`designs/`、`psd/`、`ui/`
   3. **询问用户**：如果上述方式都未找到设计稿文件，再向用户询问文件路径

5. **判断是否为多语言项目**：

   **检查项目中是否存在 i18n / 多语言机制，这直接影响图片的导出策略。**

   判断依据（满足任一即为多语言项目）：
   - 存在语言包目录（`src/langs/`、`src/locales/`、`src/i18n/` 等）
   - `package.json` 中有 `vue-i18n`、`@nuxtjs/i18n`、`i18next`、`react-intl`、`next-intl` 等国际化依赖
   - 代码中使用了 `$t()`、`t()`、`useTranslation`、`<FormattedMessage>` 等国际化 API
   - 图片资源目录按语种分子目录（如 `assets/images/en/`、`assets/images/zh/` 等）
   - 代码中根据语种动态加载图片（如 `require(\`@/assets/images/${lang}/banner.png\`)` ）

   如果是多语言项目，记录以下信息：
   - 项目支持的语种列表（如 `en`、`de`、`fr`、`es`、`pt` 等）
   - 图片资源的多语言组织方式：
     - **按语种分目录**：如 `images/en/banner.png`、`images/de/banner.png`
     - **按语种命名**：如 `banner_en.png`、`banner_de.png`
     - **代码动态引用**：通过变量拼接语种路径
   - 公共图片目录（不区分语种的图片放在哪里）

   确认后标注：`🌍 多语言项目（支持 N 种语言：en, de, fr, ...）` 或 `🔤 单语言项目`

6. **判断工作模式**：

   **根据用户需求和代码现状，判断进入哪种工作模式。后续所有步骤的执行深度都依赖此判断。**

   | 模式 | 触发条件 | 流程差异 |
   |------|---------|---------|
   | **🆕 新建模式** | 需要从零实现新页面/新组件/新模块 | 走完整流程（含第三步完整方案 + 第四步编写代码） |
   | **🔄 迭代模式** | 代码已存在，需要替换图片/修改样式/调整布局/新增少量元素 | 简化第三步，第四步按需修改或跳过，直接进入图片处理 |

   **新建模式判断**（满足任一即触发）：
   - 用户要求实现/开发一个新页面、新组件、新模块
   - 目标代码文件不存在（需要新建 `.vue`/`.jsx`/`.html`/`.tsx` 等文件）
   - 用户明确表达从零开始的意图
   
   匹配词条：
   > 实现这个页面、做这个活动页、把设计稿做出来、新建页面、开发这个模块、从零开始写、搭建这个页面、实现设计稿、根据设计稿开发、做一个新页面、创建组件、写一个新的、帮我实现、帮我做出来、按设计稿写代码、还原这个设计稿、开发新功能页面、把设计稿还原成代码、按设计稿写页面、实现这个功能

   **迭代模式判断**（满足任一即触发）：
   - 代码文件已存在，用户要求在现有基础上修改
   - 用户要求替换/新增图片资源
   - 用户要求调整样式/布局/局部修改
   
   匹配词条：
   > 替换图片、换成新设计稿的图、导出这几张图、更新图片、切图放到项目里、改一下样式、调整布局、加一个模块、改一下这个区域、按设计稿改、图片换一下、从设计稿拿素材、改页面、新增图片、增加语言的图片、多语言图片导出、修改这个组件、把图换了、用设计稿的图、设计走查、对比设计稿修正、视觉还原调整、补充图片资源、新语言支持需要图片、换图、加图、改图

   **无法判断时**：
   - 检查用户指定的目标文件/页面是否已存在
     - 文件不存在 → 新建模式
     - 文件已存在 → 迭代模式
   - 如果仍无法确定 → 询问用户："目标页面/组件是已有的还是需要新建的？"

   确认后标注：`🆕 新建模式` 或 `🔄 迭代模式`

> ✅ **第二步完成** → 立即进入第三步：确定实现方案。

### 第三步：确定实现方案

根据工作模式的不同，确定不同深度的实现方案。

#### 新建模式：完整实现方案

当进入新建模式时，需要制定完整的页面/组件实现方案：

1. **确认项目开发规范**：
   - 读取项目中已有的代码文件，确认代码风格和技术选型
   - Vue 2 项目 → 参考 `vue2-development-guide` skill 的开发规范
   - Vue 3 项目 → 遵循 Composition API 写法，匹配项目已有风格
   - React 项目 → 遵循函数组件 + Hooks 写法，匹配项目已有风格
   - Nuxt/Next.js 项目 → 遵循框架约定式路由和页面结构
   - 纯 HTML/CSS → 语义化 HTML + 项目已有的 CSS 规范（BEM/SCSS/Tailwind 等）
   - **核心原则：读项目已有代码，匹配已有风格，不引入新的技术栈或规范**

2. **划分页面结构**：
   结合设计稿图层结构和用户需求，规划页面的 HTML 结构：
   - 将设计稿划分为若干个语义化区块（Header、Content、Footer、Sidebar 等）
   - 确定各区块对应的 HTML 结构和 CSS 布局方式（flex/grid/定位）
   - 确定哪些区块需要拆分为独立组件（复用性高/逻辑独立的部分）
   - 确定各区块之间的间距、层级关系

3. **确定视觉元素的实现方式**：
   对设计稿中的每个视觉元素逐一判断用代码还是图片实现：
   
   | 元素类型 | 代码实现（HTML/CSS） | 图片实现（导出 PNG） |
   |---------|--------------------|--------------------|
   | 纯色/渐变背景 | ✅ CSS background/gradient | — |
   | 复杂装饰性背景 | — | ✅ 导出为背景图 |
   | 纯色文字 | ✅ CSS font 样式 | — |
   | 特效文字（渐变/描边/3D） | — | ✅ 导出为图片 |
   | 简单图标 | ✅ SVG/iconfont | — |
   | 复杂图形/插画 | — | ✅ 导出为图片 |
   | 按钮 | ✅ HTML + CSS 样式 | 背景可能用图片 |
   | 分割线/边框 | ✅ CSS border/hr | — |
   | 动态数据（倒计时/价格等） | ✅ JS + HTML 渲染 | — |

4. **确定图片清单和去重方案**：
   - 列出需要从设计稿导出的所有图片
   - 对每张图片预判去重需求（基于即将编写的代码结构判断哪些子图层会被代码独立渲染）
   - 整理为图片导出清单格式（同第六步的清单格式）

5. **输出方案摘要**（供自己后续步骤参考）：
   ```
   📐 实现方案摘要
   
   页面结构：
   - Header Section: flex 布局, 背景图 header-bg.png
   - Prize Section: grid 布局 2×3, 每个奖品卡独立组件
   - Rule Section: 纯文字区域, CSS 实现
   - Popup: 规则弹窗, v-if 控制显隐
   
   代码实现（CSS）：标题文字、规则文字、按钮文案
   图片实现（导出）：页面背景、奖品卡背景、按钮背景、弹窗装饰
   
   预估图片：5 张公共 + 2 张多语种×5 = 15 个文件
   ```

#### 迭代模式：简化方案

当进入迭代模式时，不需要重新规划整体结构，只需确认修改范围：

1. **确认修改范围**：（与第二步第 3 条相同，此处强调确认）
   - 用户要修改/替换/新增哪些内容
   - 涉及哪些文件和代码区域

2. **确定图片清单**：
   - 需要替换哪些图片（对比新旧设计稿差异）
   - 需要新增哪些图片
   - 是否需要调整代码（如尺寸变更、新增元素需要加 HTML/CSS）

3. **快速判断是否需要改代码**：

   对每张需要替换或新增的图片，逐一检查代码中是否已有对应的展示结构（`<img>` 标签、`background-image`、伪元素等），然后根据结果判断：

   | 场景 | 代码现状 | 判断结果 |
   |------|----------|----------|
   | 替换同尺寸图片 | 代码中已有对应的图片引用且能正常展示 | → 不需要改代码，直接进第五步 |
   | 替换同尺寸图片 | 代码中缺少展示该图片的结构（如缺少 `<img>` 标签或 `background-image` 声明） | → 需要添加图片展示代码 |
   | 替换/新增多语种图片 | 代码中已有语种切换逻辑且能正确加载各语种图片 | → 不需要改代码，直接进第五步 |
   | 替换/新增多语种图片 | 代码中缺少语种切换逻辑（如缺少根据 `lang` 变量动态拼接图片路径、缺少语种条件判断等） | → 需要补充语言相关逻辑 |
   | 图片尺寸变更 | 代码中已有引用 | → 需要修改 CSS 尺寸值 |
   | 新增图片元素 | 代码中无对应结构 | → 需要添加 HTML 标签和 CSS |
   | 布局/结构调整 | — | → 需要修改 HTML 结构和 CSS 布局 |

   **关键检查点**：
   - 即使是「替换」操作，也必须确认代码中确实存在能渲染该图片的完整链路（引用路径正确、有对应的 DOM 元素、CSS 中有 `background-image` 声明等）。如果代码中缺少任何环节导致图片无法显示，则需要补充代码。
   - **多语言项目额外检查**：当图片为多语种图片时，还必须确认代码中存在根据当前语种加载对应图片的逻辑（如动态路径拼接 `` require(`@/assets/images/${lang}/btn.png`) ``、语种映射表、条件渲染等）。如果代码中只有固定路径引用（如硬编码 `en/btn.png`），则新增语种的图片无法被展示，需要补充语种切换逻辑。

> ✅ **第三步完成** → 立即进入第四步：编写/修改代码（迭代模式下如判断为「不需要改代码」则跳过第四步，直接进入第五步）。

### 第四步：编写/修改代码

根据工作模式执行不同深度的代码编写。

#### 新建模式：完整编写代码

按照第三步确定的实现方案，编写完整的页面/组件代码：

1. **创建文件结构**：
   - 创建页面/组件文件（`.vue`/`.jsx`/`.html` 等）
   - 创建样式文件（`.scss`/`.css`/`.less` 等，按项目规范）
   - 如果需要拆分子组件，创建组件文件

2. **编写 HTML 结构**：
   - 按第三步划分的区块编写语义化 HTML
   - 图片位置使用占位方式：
     - `<img>` 标签：先写结构，`src` 留空或用占位图 `src=""`
     - `background-image`：先写容器和类名，CSS 中 `background-image` 暂时不写或注释
   - 动态内容使用数据绑定（如 `{{title}}`、`{data.name}` 等）

3. **编写 CSS 样式**：
   - 布局样式（flex/grid/定位/间距）
   - 文字样式（从设计稿文字图层提取的 font-size/color/font-weight 等）
   - 容器尺寸和背景属性（背景色、圆角、阴影等 CSS 可实现的部分）
   - 图片容器预留（设置 width/height 为设计稿中的尺寸，`background-size: contain/cover`）
   - **尺寸单位遵循 `image-sizing-guide` skill 规则**：移动端 ÷100 转 rem，PC 端直接 px

4. **编写业务逻辑**（如有）：
   - 数据获取和状态管理
   - 交互逻辑（点击事件、弹窗控制、Tab 切换等）
   - 动态渲染逻辑（列表循环、条件显示等）
   - 路由配置（如果是新页面需要注册路由）

5. **代码编写原则**：
   - 匹配项目已有的代码风格和命名规范
   - 组件化程度参考项目已有的拆分粒度
   - 不引入项目中未使用的新依赖/新库
   - 国际化文字使用项目已有的 i18n 方案（如 `$t('key')`）
   - **先完成代码骨架，图片引用留空**，等第七步导出图片后再补充

#### 迭代模式：按需修改代码

根据第三步的"快速判断"结果执行：

- **不需要改代码** → 直接跳到第五步
- **需要修改 CSS 尺寸** → 在第七步导出图片获得实际尺寸后一并修改
- **需要添加 HTML/CSS** → 按最小改动原则，只添加必要的新元素和样式
- **需要调整布局** → 修改涉及的 CSS 布局属性，不动其他无关代码

**迭代模式编写原则**：
- 改动范围最小化，只动必要的部分
- 不重构已有代码（即使发现写法不够好）
- 新增代码风格与周围代码保持一致
- 如果改动较大（如加了一整个新区块），按新建模式中的编写原则执行该区块

**关于测试**：当第四步涉及新增或修改功能代码时（新建模式下必须、迭代模式下按需），必须编写对应的单元测试或属性测试用例，验证组件/功能逻辑的正确性（如 props 传递、事件触发、数据渲染、条件显示等）。测试用例的编写遵循项目已有的测试规范和目录结构。明确不编写 Playwright E2E 测试脚本——视觉还原的截图验证由第九步统一完成。

> ✅ **第四步完成** → 立即进入第五步：分析并处理图片资源。

### 第五步：分析并处理图片资源

**本步骤与第三步的关系**：
- 第三步是方案规划（粗粒度）：列出大致需要哪些图片、预判去重方向
- 本步骤是基于实际代码的精确分析（细粒度）：以第四步写好的代码（或已有代码）为基准，逐张图片做精确的图层对应和去重分析
- 新建模式下：第四步的代码是自己刚写的，去重分析更直接——自己清楚哪些元素已通过代码独立渲染，无需逐行阅读代码推断
- 迭代模式下：代码是项目中已有的，需要仔细阅读相关代码区域，确认哪些元素已独立实现

根据项目代码和用户需求，对每张需要的图片进行分类分析：

#### 替换类图片分析

当项目代码中已存在对应图片引用时，判定为替换：

1. **定位原图**：在项目中找到原图片文件路径
2. **分析原图信息**：
   - 获取原图的实际像素尺寸（使用 Pillow 获取图片尺寸）
   - 记录原图在代码中的引用方式（import 路径、CSS url() 等）
   - 记录原图对应的 CSS 尺寸设置（width/height 值）
3. **分析设计稿中对应内容**：
   - 确定设计稿中哪个图层/区域对应这张图片
   - 对比新旧尺寸是否一致，如不一致需要同步更新代码中的尺寸设置
4. **记录替换描述**：清晰描述图片的内容和用途，用于从设计稿中精准定位导出

#### 新增类图片分析

当项目代码中不存在对应引用时，判定为新增：

1. **确定图片内容**：分析设计稿中需要导出的图层/区域
2. **确定存放路径**：根据项目的资源目录结构确定新图片应该放在哪里
3. **确定引用方式**：规划代码中如何引入这张图片（import、require、相对路径等）
4. **记录新增描述**：清晰描述图片的内容和用途

**注意**：新增图片不需要预先考虑图片尺寸问题，尺寸在导出后根据实际像素值设置。

#### 文字图层处理分析（关键）

**设计稿中的文字内容必须逐一判断：是导出为图片，还是用 CSS 实现。**

**判断规则**：

1. **文字需要导出为图片的情况**：
   - 文字带有复杂的视觉效果（渐变色、描边、阴影、纹理填充、3D 效果等），CSS 难以精确还原
   - 文字与背景/装饰元素紧密结合为一个整体视觉（如艺术字标题嵌入在复杂背景中）
   - 使用了特殊字体且项目未引入该字体（用户未要求引入 webfont）
   - 代码中已有对应位置使用图片方式显示文字的模式

2. **文字用 CSS 实现的情况**：
   - 纯色文字（单色，无特殊效果）
   - 代码中对应位置已使用文本标签（`<span>`、`<p>`、`<h1>` 等）渲染
   - 多语言项目中通过 i18n 动态显示不同语言的文案
   - 文字内容是动态的（如用户名、倒计时、数据等）
   - 常规字体（系统字体或项目已引入的 webfont）

**文字用 CSS 实现时的样式提取**：

当判定文字用 CSS 实现时，直接从 `list-layers` 输出的 JSON 中读取 TEXT 图层的 `textStyle` 字段，即可获得完整的样式信息：

```
# 从 list-layers 输出的 textStyle 字段可直接获取：
# - fontSize（字号，px）
# - fontName（字体 PostScript 名称）
# - fauxBold / fauxItalic（仿粗体 / 仿斜体）
# - color（颜色，十六进制）
# - justification（对齐方式：LEFT / CENTER / RIGHT）
# - leading（行距，px 或 "auto"）
# - tracking（字间距，整数值）
# - contents（文本内容）
```

**提取方式**：`list-layers` skill 已支持输出 TEXT 图层的样式信息。在读取图层结构时（使用 `list-layers` skill），对 `type: "TEXT"` 的图层，会自动输出 `textStyle` 字段，包含字号、字体、粗细、颜色、对齐方式、行距、字间距和文本内容：

```json
{
  "path": "Header/title",
  "name": "title",
  "type": "TEXT",
  "visible": true,
  "textStyle": {
    "fontSize": "36px",             // 字号（px）
    "fontName": "PingFangSC-Semibold", // 字体 PostScript 名称
    "fauxBold": false,              // 是否仿粗体
    "fauxItalic": false,            // 是否仿斜体
    "color": "#ff6b35",             // 颜色（十六进制）
    "justification": "CENTER",      // 对齐方式（LEFT / CENTER / RIGHT）
    "leading": "48px",              // 行距（px），自动行距时为 "auto"
    "tracking": 50,                 // 字间距（整数值，0 为默认）
    "contents": "Summer Sale"       // 文本内容
  }
}
```

直接从图层结构 JSON 中读取 `textStyle` 字段即可获取样式数据，无需额外操作。如果某些字段提取失败（PSD 文件结构差异），则该字段值为 `null`，此时通过视觉观察设计稿效果图来估算缺失的值。

**字段映射到 CSS 的规则**：

| textStyle 字段 | CSS 属性 | 转换说明 |
|---------------|----------|----------|
| `fontSize` | `font-size` | 移动端 ÷100 转 rem，PC 端直接用 px |
| `fontName` | `font-family` | PostScript 名称需映射为 CSS font-family（如 `PingFangSC-Semibold` → `'PingFang SC', sans-serif`） |
| `fauxBold: true` | `font-weight: bold` | fauxBold 为 true 时设为 bold/700 |
| `fauxItalic: true` | `font-style: italic` | fauxItalic 为 true 时设为 italic |
| `color` | `color` | 直接使用十六进制值 |
| `justification` | `text-align` | LEFT→left, CENTER→center, RIGHT→right |
| `leading` | `line-height` | 可计算比例（leading ÷ fontSize），"auto" 时不设置或使用 normal |
| `tracking` | `letter-spacing` | tracking ÷ 1000 × fontSize = letter-spacing（px），为 0 时不设置 |

提取后生成对应的 CSS 样式：

```scss
// 示例：从 textStyle 字段直接转换为 CSS 样式
// textStyle: { fontSize: "36px", fontName: "PingFangSC-Semibold", fauxBold: false, color: "#ff6b35", leading: "48px", tracking: 50, justification: "CENTER" }
.title-text {
  font-size: 32px;           // PC 端直接用 px / 移动端转 rem（÷100）→ 0.36rem（36÷100）
  font-family: 'PingFang SC', sans-serif;  // 从 fontName "PingFangSC-Semibold" 映射
  font-weight: 600;          // fontName 含 "Semibold"，映射为 600
  color: #ff6b35;            // 直接使用 textStyle.color
  line-height: 1.33;         // leading 48px ÷ fontSize 36px ≈ 1.33
  letter-spacing: 1.8px;     // tracking 50 ÷ 1000 × 36 = 1.8px（移动端 ÷100 转 rem）
  text-align: center;        // justification "CENTER" → center
}
```

**样式提取注意事项**：
- 字号单位遵循 `image-sizing-guide` 规则：移动端 ÷ 100 转 rem，PC 端直接 px
- 颜色值直接使用 textStyle.color（十六进制格式），有透明度需求时手动改为 RGBA
- fontName 是 PostScript 名称，需要映射为 CSS font-family（如 `ArialMT` → `Arial`，`PingFangSC-Regular` → `'PingFang SC'`）
- 字重判断：优先看 fontName 中的后缀（`-Bold`/`-Semibold`/`-Medium`/`-Regular`/`-Light`），其次看 fauxBold 字段
- line-height 如果能整除为比例值（如 48px / 32px = 1.5）则使用比例，leading 为 "auto" 时不设置该属性
- letter-spacing 计算公式：tracking ÷ 1000 × fontSize（px），为 0 时不写该属性
- 如果设计稿使用的字体项目中未引入，优先使用项目已有的相近字体作为替代，并在摘要中备注

**多语言图片尺寸统一规则（关键）**：

**核心原则：多语言项目中，同一功能/位置的各语种图片必须尽量保持相同的宽高尺寸，确保切换语言时页面布局不跳动。**

---

**场景一：设计稿中同时存在多个语种图层，需要分别导出**

当设计稿中同一个功能或位置存在多个语种的图层（如多语种按钮、多语种标题）需要分别导出时，执行以下流程：

1. **分别导出各语种图片**：按正常多语种导出流程，为每个语种分别导出 PNG 图片（此时各语种图片尺寸可能不同）

2. **收集所有语种的实际尺寸**：
   ```
   示例：
   - EN: 320×80
   - DE: 380×80（德语最宽）
   - FR: 350×85（法语最高）
   - ES: 340×80
   ```

3. **确定统一尺寸**：取所有语种中的**最大宽度**和**最大高度**作为统一画布尺寸
   ```
   统一尺寸 = 380×85（取最大宽 380，最大高 85）
   ```

4. **统一尺寸处理**：使用预置脚本 `img_unify_size.py` 的 `unify` 命令，自动为所有语种图片创建统一尺寸的透明画布并居中放置：

   ```powershell
   # unify 命令：自动取最大宽高，各图片裁剪透明区域后居中放置到统一画布
   ~/.kiro/skills/design-to-code/.venv/Scripts/python.exe `
     ~/.kiro/skills/design-to-code/scripts/img_unify_size.py `
     unify <图片1.png> <图片2.png> <图片3.png> ...

   # 也可以指定目标尺寸（如需要与已有图片尺寸对齐）
   ~/.kiro/skills/design-to-code/.venv/Scripts/python.exe `
     ~/.kiro/skills/design-to-code/scripts/img_unify_size.py `
     unify <图片1.png> <图片2.png> --target-width 380 --target-height 85
   ```

5. **验证**：确认所有语种图片尺寸一致后，放入项目对应目录

---

**场景二：代码中已有其他语种图片，需要导出新语种图片**

当项目中已存在某些语种的图片，用户要求新增一个新语种的图片时，新语种图片的尺寸必须**优先与已有语种图片保持一致**：

1. **获取已有语种图片的尺寸**：读取项目中已有的同功能/同位置的其他语种图片的宽高

2. **导出新语种图片**：从设计稿中导出新语种的原始图片

3. **对比尺寸并处理**：

   **情况 A：新导出图片尺寸与已有一致** → 直接使用，无需处理

   **情况 B：新导出图片尺寸偏大（宽或高超出已有尺寸）** → 优先通过裁剪透明区域解决：
   ```powershell
   # trim 命令：裁剪透明区域，并适配到目标尺寸（居中放置）
   & "$env:USERPROFILE\.kiro\skills\design-to-code\.venv\Scripts\python.exe" `
     "$env:USERPROFILE\.kiro\skills\design-to-code\scripts\img_unify_size.py" `
     trim <新语种图片路径> --target-width <目标宽度> --target-height <目标高度>
   
   # 如果裁剪后仍超出目标尺寸，脚本会输出警告，此时进入情况 D 处理
   ```

   **情况 C：新导出图片尺寸偏小（宽或高小于已有尺寸）** → 创建与已有相同尺寸的透明画布，将新图片居中放置：
   ```powershell
   # expand 命令：扩展画布到目标尺寸，原图居中放置
   & "$env:USERPROFILE\.kiro\skills\design-to-code\.venv\Scripts\python.exe" `
     "$env:USERPROFILE\.kiro\skills\design-to-code\scripts\img_unify_size.py" `
     expand <新语种图片路径> --target-width <目标宽度> --target-height <目标高度>
   ```

   **情况 D：裁剪透明区域后仍超出目标尺寸，且无法调整** → 作为最后手段，通过修改代码兼容不同语种的不同图片尺寸：
   - 在代码中为该语种单独设置图片容器尺寸
   - 或使用 `max-width`/`max-height` + `object-fit: contain` 等 CSS 方案自适应
   - 在摘要报告中标注此情况并说明代码修改内容

---

**处理优先级总结**：

```
多语种图片尺寸不一致时的处理优先级：

1️⃣ 裁剪透明区域（尺寸偏大时）→ 最优先、无损
2️⃣ 扩展透明画布 + 居中放置（尺寸偏小时）→ 次优先、无损
3️⃣ 修改代码兼容不同尺寸（以上方式无法解决时）→ 最后手段

绝不通过缩放/拉伸图片内容来统一尺寸（会导致模糊或变形）
```

**目的**：确保各语种切换时图片容器尺寸不变，页面布局不跳动。

**关于 i18n 语言包协作**：

如果文字内容用 CSS 实现且项目是多语言项目：
- 文字内容（文案）的翻译写入语言包 → 需配合 `i18n-locale-converter` skill 处理
- 本 skill 只负责图片和样式相关工作，不直接修改语言包文件
- 在摘要报告中列出需要添加到语言包的文案内容，提醒用户后续使用 `i18n-locale-converter` skill 完成

#### 普通图片图层去重分析（关键）

**核心规则：导出普通图片（非全区域背景图的独立图片元素，无论通过 `<img>` 标签、独立 `background-image`、CSS `content`、`::before/::after` 伪元素或其他任何方式渲染）时，如果该图片对应的是一个图层组（group），必须检查组内是否包含代码中已独立渲染的子元素图层，并在导出时隐藏这些图层，避免图片中出现与代码重复的内容。**

这个逻辑与背景图去重类似，但适用范围不同。背景图去重关注的是"大面积背景上叠放的独立 HTML 元素"，而普通图片去重关注的是"图片图层组内部包含的、已被代码单独处理的子元素"。无论图片最终以何种方式渲染到页面上（img 标签、背景图、伪元素等），只要它对应的是一个图层组，就需要做去重分析。

**适用场景**：

- 一个图层组导出为单张图片（无论代码中以 `<img>`、`background-image`、伪元素或其他方式渲染），但组内某些子图层已在代码中通过其他方式独立渲染
- 例：奖品卡片图层组中包含奖品名称文字，而代码中奖品名称通过 `<span>{{prizeName}}</span>` 动态渲染
- 例：按钮图层组中包含按钮文案文字，而代码中按钮文案通过 i18n 动态渲染
- 例：商品卡片图层组中包含价格标签，而代码中价格通过 JS 动态展示

**分析流程**：

1. **判断图片是否为图层组**：
   - 如果该图片对应的是单个图层（pixel/shape），无需去重，直接导出
   - 如果该图片对应的是一个图层组（group），进入去重分析

2. **分析图层组内的子图层**：
   逐一检查图层组内的每个子图层，判断其内容在代码中是否已独立实现：
   - 文字子图层（type）：代码中是否有对应的 `<span>`/`<p>` 等文本标签渲染该文字？
   - 图片子图层（pixel）：代码中是否有其他独立的 `<img>` 标签引用该元素？
   - 子图层组（group）：代码中是否有独立组件/元素渲染该区域？

3. **确定需要隐藏的子图层**：
   
   ```
   设计稿图层结构示例（奖品卡片）：
   
   ├── Prize Card (group) ← 整组导出为一张图片
   │   ├── [👁] card-bg (pixel) ← 保留：卡片背景底图
   │   ├── [👁] card-border (shape) ← 保留：卡片边框装饰
   │   ├── [👁] prize-name "iPhone 15" (type) ← 隐藏❗（代码中用 <span>{{prize.name}}</span> 动态渲染）
   │   ├── [👁] prize-price "$999" (type) ← 隐藏❗（代码中用 <span>{{prize.price}}</span> 动态渲染）
   │   └── [👁] shine-effect (pixel) ← 保留：装饰性光效
   ```
   
   最终导出：`card-bg` + `card-border` + `shine-effect` 合并为卡片图片（不含文字）

4. **生成隐藏图层清单**：
   与背景图去重类似，对每张需要去重的普通图片列出：
   - **需要隐藏的子图层**：组内已被代码独立实现的元素
   - **保持原样的子图层**：纯视觉/装饰性内容，代码中未独立实现

**判断是否需要隐藏的决策树**（普通图片版）：

```
该图层组内的子图层内容，在代码中是否已有独立元素渲染？
├── 是 → 导出时隐藏该子图层
│   ├── 动态文字：代码中通过数据绑定/i18n 动态显示 → 隐藏
│   ├── 独立图片：代码中用另一个 <img> 单独引用 → 隐藏
│   ├── 交互元素：代码中有对应的按钮/链接/输入框 → 隐藏
│   └── 状态相关：代码中根据状态动态切换显示内容 → 隐藏
└── 否 → 保留在图片中一起导出
    ├── 固定装饰（边框、光效、阴影等）→ 保留
    ├── 静态视觉元素（不需要交互或翻译）→ 保留
    └── 图形背景（渐变、色块、纹理等）→ 保留
```

**常见需要隐藏的情况**（普通图片）：

| 图层组内的子图层 | 代码中的实现方式 | 处理 |
|----------------|----------------|------|
| 商品名称文字 | `<span>{{item.name}}</span>` 数据绑定 | 隐藏 |
| 价格/数量文字 | `<span>{{item.price}}</span>` 动态数据 | 隐藏 |
| 按钮文案 | i18n 多语言文字 `{{$t('btnText')}}` | 隐藏 |
| 状态标签（如"已售罄"） | 代码中根据状态 `v-if` 显示不同文案 | 隐藏 |
| 用户头像占位 | `<img :src="user.avatar">` 动态图片 | 隐藏 |
| 角标/徽章数字 | 代码中动态计算显示 | 隐藏 |
| 卡片背景/边框 | 无独立代码实现，属于图片本身 | **保留** |
| 装饰图案/光效 | 无独立代码实现 | **保留** |
| 固定 icon 图标 | 无独立引用，属于整体视觉 | **保留** |

**与背景图去重的区别**：

| 对比项 | 普通图片去重 | 背景图去重 |
|--------|------------|-----------|
| 适用对象 | 非全区域背景的独立图片（`<img>`、独立 `background-image`、伪元素等任何渲染方式） | `background-image` 大面积区域背景 |
| 去重范围 | 图片对应的图层组**内部**子图层 | 背景覆盖区域内**所有**已独立渲染的元素 |
| 典型场景 | 卡片、按钮、奖品框等组件图片 | 页面区块背景、头部背景、弹窗背景 |
| 隐藏内容 | 组内的动态文字、独立引用的子图片 | 区域内的标题、按钮、图标、动态组件 |
| 其他区域处理 | 不需要（只关注组内） | 需要隐藏不属于该背景的其他顶层图层组 |

**普通图片导出清单格式补充**：

当普通图片需要去重时，在导出清单下方增加隐藏图层说明：

```
#### 🖼️ 普通图片导出详情

#### 图片：奖品卡片（prize-card.png）

**导出方式**：composite 合并导出
**对应图层组**：Prize Card

**❌ 需隐藏的子图层（代码中已独立实现 — 基于代码分析）**：
- ❌ Prize Card/prize-name — 代码中用 `<span>{{prize.name}}</span>` 动态渲染
- ❌ Prize Card/prize-price — 代码中用 `<span>{{prize.price}}</span>` 动态渲染

**✅ 保持原样的子图层（属于图片本身的视觉内容）**：
- ✅ Prize Card/card-bg — 卡片背景
- ✅ Prize Card/card-border — 边框装饰
- ✅ Prize Card/shine-effect — 装饰光效
（这些图层保持设计稿原始 visible 状态，不在 visibility_changes 中设置）
```

**特殊情况：无需去重的普通图片**：

以下情况直接导出，不需要做去重分析：
- 图片对应的是单个图层（非图层组）— 没有子图层可去重
- 图层组内所有子图层都是纯视觉元素，代码中没有任何独立实现的对应内容
- 图片是纯装饰/图标类（如 logo、icon、分割线等），不包含任何动态/文字内容
- 整个图层组作为一个完整的不可分割视觉元素导出（如复杂合成的艺术图形）
- **智能对象（smartobject）类型的图层** — Photoshop 无法通过 COM 接口读取智能对象内部嵌套的 PSD/PSB 结构，视为不可拆分的单一图层，直接导出其栅格化外观，不做内部去重分析

#### 背景图图层去重分析（关键）

**核心规则：导出背景图时，必须隐藏所有已通过代码（HTML/CSS/JS）单独渲染的元素图层，避免背景图中出现重复内容。**

这是最容易出错的环节。设计稿是完整的视觉效果图，包含了所有元素，但在实际前端实现中，很多元素是通过代码单独渲染的（如文字、按钮、图标、列表项等），背景图只需要提供这些元素的底层背景/装饰。

**分析流程**：

1. **识别背景图需求**：

   **背景图的定义**：在代码中作为某个容器的 `background-image` 使用，其上方叠放了其他独立的 HTML 元素（文字、按钮、图片、组件等）的图片。背景图本身不承载交互和语义，只提供视觉底层。

   **背景图的粒度层级**：

   | 粒度 | 描述 | 典型场景 | 对应代码 |
   |------|------|----------|----------|
   | 页面级背景 | 整个页面/视口的底层背景 | 活动页整屏背景、落地页背景 | `body` / `.page-wrapper` 的 `background-image` |
   | 区块级背景 | 页面中某个独立区域的背景 | 头部区域背景、奖品区背景、规则区背景 | `.header-section` / `.prize-section` 的 `background-image` |
   | 组件级背景 | 单个组件/模块的背景 | 卡片背景、按钮背景、输入框背景 | `.card` / `.btn` 的 `background-image` |
   | 弹窗级背景 | 弹窗/浮层的背景装饰 | 中奖弹窗背景、规则弹窗背景 | `.popup-inner` / `.modal-content` 的 `background-image` |

   **判定某张图片是否为背景图的规则**（满足以下任一即为背景图）：

   - **从代码判断**（迭代模式 / 已有代码时）：
     - 代码中该图片通过 `background-image` / `background` CSS 属性引用
     - 该图片对应的容器内部还有其他 HTML 子元素（文字、按钮等）独立渲染在其上方
   
   - **从设计稿结构判断**（新建模式 / 代码尚未编写时）：
     - 该图层组内既有大面积的底层视觉图层（渐变、纹理、装饰），又有明显属于独立 UI 元素的子图层（文字、按钮、图标、卡片等）
     - 底层视觉图层的面积覆盖了整个图层组的范围（或大部分范围），其他子图层「浮」在其上
     - 按正常前端实现方式，这些「浮在上面」的子元素会通过独立的 HTML 标签渲染（而非和底层融为一张图片）

   **背景图 vs 普通图片的关键区别**：

   ```
   背景图：
   - 图片作为容器的 background-image
   - 容器内部还有其他 HTML 子元素叠放在图片上方
   - 去重时需要隐藏：容器内所有已独立渲染的子元素 + 其他无关区域

   普通图片（图层组导出）：
   - 图片作为独立元素渲染（<img>、独立的小 background-image、伪元素等）
   - 图片上方通常没有其他 HTML 元素叠放（或只有极少的叠放元素）
   - 去重时只需要隐藏：图层组内部已被代码独立渲染的子图层
   ```

   **容易混淆的边界情况**：

   | 情况 | 判定 | 理由 |
   |------|------|------|
   | 一张大图作为整个区域背景，上面有文字和按钮 | 背景图 | 上面有独立 HTML 元素叠放 |
   | 一张卡片底图，上面只有动态文字 | 背景图 | 文字独立渲染在其上方 |
   | 一张卡片底图，上面没有任何独立元素 | 普通图片 | 没有叠放内容，整组导出即可 |
   | 一个按钮的背景图，上面有按钮文案 | 背景图（组件级） | 文案通过代码渲染 |
   | 一个纯装饰图标（无子元素叠放） | 普通图片 | 没有叠放，直接导出 |
   | 弹窗内的装饰底图，上面有标题和关闭按钮 | 背景图（弹窗级） | 上面有独立 HTML 元素 |

2. **分析代码中已独立渲染的元素**：
   仔细阅读该背景图覆盖区域内的代码，找出所有已通过 HTML/CSS 独立实现的内容：
   - 文字内容（标题、描述、按钮文案等）— 通过 `<span>`、`<p>`、`<h1>` 等标签渲染
   - 图标/小图片 — 通过独立的 `<img>` 标签或 `background-image` 渲染
   - 按钮 — 通过独立元素+独立背景图实现
   - 列表项/卡片 — 通过循环渲染的独立组件
   - 动态内容 — 通过 JS 动态生成的元素（倒计时、进度条等）

3. **确定导出时需要隐藏的图层**：
   将设计稿中对应上述已独立渲染内容的图层标记为"导出时隐藏"：
   
   ```
   设计稿图层结构示例（活动页头部区域）：
   
   ├── Header Section
   │   ├── [👁] gradient-bg (pixel) ← 需要导出为背景图
   │   ├── [👁] decorative-stars (pixel) ← 需要导出（装饰元素，代码中没有单独实现）
   │   ├── [👁] title-text "限时活动" (type) ← 导出时隐藏❗（代码中用 <h1>{{$t('title')}}</h1> 渲染）
   │   ├── [👁] countdown-box (group) ← 导出时隐藏❗（代码中用 JS 动态渲染倒计时）
   │   ├── [👁] start-button (group) ← 导出时隐藏❗（代码中用独立的 <button> + 单独背景图实现）
   │   └── [👁] avatar-frame (pixel) ← 导出时隐藏❗（代码中用独立 <img> 渲染）
   ```
   
   最终只导出：`gradient-bg` + `decorative-stars` 合并为背景图

4. **生成隐藏图层清单（基于代码分析）**：
   在图片导出清单中，对每张背景图必须明确列出：
   - **需要隐藏的图层**：通过分析代码确认的、已在代码中独立实现的元素对应的图层
   - **需要隐藏的其他区域**：不属于该背景图范围的其他顶层图层组
   - **保持原样的图层**：未被代码独立实现的装饰性图层（渐变、纹理、光效等），不列入隐藏清单，保持设计稿原始可见性

**判断是否需要隐藏的决策树**：

```
该图层内容在代码中是否已有独立的 HTML 元素渲染？
├── 是 → 导出背景图时必须隐藏该图层
│   ├── 文字类：代码中用文本标签渲染 → 隐藏
│   ├── 图片类：代码中用独立 <img> 或独立 background-image 渲染 → 隐藏
│   ├── 交互类：代码中用按钮/输入框等独立元素渲染 → 隐藏
│   └── 动态类：代码中用 JS 动态生成 → 隐藏
└── 否 → 保留在背景图中一起导出
    ├── 纯装饰（星星、光效、纹理等）→ 保留
    ├── 固定不变的视觉元素（无需交互/无需翻译）→ 保留
    └── 渐变/色块背景 → 保留
```

**常见需要隐藏的情况**：

| 设计稿中的图层 | 代码中的实现方式 | 处理 |
|---------------|----------------|------|
| 标题文字 | `<h1>{{title}}</h1>` 或 i18n 文字图片 | 隐藏 |
| 按钮（含背景+文字） | `<button>` + 独立按钮背景图 | 隐藏 |
| 用户头像框 | `<img :src="avatar">` | 隐藏 |
| 奖品图标 | 独立的 `<img>` 循环渲染 | 隐藏 |
| 倒计时数字 | JS 动态更新的 `<span>` | 隐藏 |
| 进度条 | CSS + JS 控制的 `<div>` | 隐藏 |
| 装饰性光效/粒子 | 无代码实现，纯视觉 | **保留** |
| 渐变底色 | 无代码实现，纯背景 | **保留** |
| 固定装饰图案 | 无代码实现 | **保留** |

**特殊情况处理**：
- 如果一个元素**部分**在代码中实现（如按钮背景由代码渲染，但按钮旁边的装饰光效在设计稿中与按钮同组），需要单独拆分：保留装饰部分，隐藏按钮部分
- 如果不确定某个图层是否在代码中已实现，优先查看代码确认，不要猜测

#### 弹窗/浮层图层分析

**设计稿中弹窗、浮层、Toast、抽屉等覆盖层组件通常以隐藏图层状态存在，需要主动识别并处理。**

**识别方法**：

1. **通过图层可见性识别**：设计稿中 `visible: false`（隐藏）的图层组，名称包含以下关键词时很可能是弹窗/浮层：
   - `popup`、`pop`、`modal`、`dialog`、`overlay`
   - `toast`、`tip`、`tooltip`
   - `drawer`、`panel`、`sheet`
   - `mask`（遮罩层）
   - 中文：`弹窗`、`浮层`、`对话框`、`提示`、`蒙层`

2. **通过图层结构识别**：
   - 图层组中包含一个全画布大小的半透明遮罩层（如 `mask`、`overlay-bg`）
   - 图层组的 z-order 位于最顶层（PSD 中最后的图层组通常是最上层）
   - 图层组内容在画布中心区域（居中的弹窗）

3. **通过代码确认**：
   - 代码中有 `v-show`、`v-if`、`display: none`、`.show()`/`.hide()` 控制的弹窗组件
   - 代码中有 Modal、Dialog、Popup、Drawer 等组件的使用

**处理流程**：

1. **列出所有弹窗/浮层**：在图层结构中找出所有疑似弹窗/浮层的隐藏图层组
2. **确认与代码的对应关系**：每个弹窗对应代码中的哪个组件/哪段逻辑
3. **分析弹窗内的图片需求**：对每个弹窗内部，按照和普通区域相同的流程分析新增/替换/背景图
4. **导出时临时显示**：导出弹窗相关图片时，需要将该弹窗图层组设为可见（`visible: true`），再进行导出

**弹窗导出注意事项**：
- 导出弹窗背景图时，同样需要执行背景图去重（隐藏弹窗内代码已独立渲染的元素）
- 遮罩层（半透明黑色背景）通常由代码实现（CSS `background: rgba(0,0,0,0.5)`），导出时应隐藏遮罩图层
- 如果弹窗有多种状态（如成功/失败/加载中），每种状态可能对应不同的隐藏图层组合，需要分别导出

**在导出清单中标注弹窗图片**：

```
#### 🪟 弹窗/浮层图片

| # | 弹窗名称 | 图片描述 | 类型 | 对应图层组 | 触发条件 |
|---|----------|----------|------|-----------|----------|
| 1 | 活动规则弹窗 | 弹窗背景装饰 | 背景图 | PopupRule（隐藏） | 点击"规则"按钮 |
| 2 | 中奖弹窗 | 恭喜中奖背景 | 背景图 | PopupWin（隐藏） | 抽奖成功时 |
| 3 | 中奖弹窗 | 奖品展示框 | 新增 | PopupWin/prize-frame | 抽奖成功时 |
```

#### 多语言图片分析（仅多语言项目）

当第二步判定为多语言项目时，**每张图片必须额外判断是公共图片还是多语种图片**：

**判断规则**：

1. **公共图片**（所有语种共用同一张）：
   - 图片中不包含任何文字内容（纯图形、背景、图标、装饰等）
   - 图片中的文字是通用的（如数字、符号、品牌名等不需要翻译的内容）
   - 代码中该图片的引用路径不含语种变量
   - 存放在公共图片目录中（如 `images/common/`）

2. **多语种图片**（每个语种需要单独的版本）：
   - 图片中包含需要翻译的文字内容（如活动标题、按钮文案、规则说明等）
   - 代码中该图片通过语种变量动态引用
   - 存放在语种子目录中（如 `images/en/`、`images/de/`）

**多语种图片的设计稿分析**：

当一张图片被判定为多语种图片时，需要分析设计稿中对应图层的结构：

1. **识别语言图层与非语言图层**：
   - 设计稿中通常将文字内容放在独立的文字图层（type 类型）或按语种分组
   - 非语言图层：背景、装饰、图标等视觉元素（各语种版本应完全相同）
   - 语言图层：包含翻译文字的图层（各语种版本内容不同）

2. **验证非语言图层一致性**：
   - 各语种版本中，除语言图层外的其他图层**应该完全相同**（位置、尺寸、内容一致）
   - 如果发现非语言图层在不同语种中有差异，需要标记并提醒用户确认是否正确

3. **验证尺寸一致性**：
   - 分析代码中各语种图片的引用方式，确认是否使用相同的 CSS 尺寸设置
   - 如果代码中所有语种共用同一个尺寸样式 → 各语种导出的图片**必须保持相同尺寸**
   - 如果代码中各语种尺寸独立设置 → 允许不同尺寸（但需标注）
   - **通常情况下，各语种图片必须保持相同尺寸**，以确保切换语言时页面布局不变

4. **导出策略**：
   - 确定设计稿中各语种图层的组织方式（按语种分组/按图层名标记语种等）
   - 为每个语种版本分别导出：隐藏其他语种的文字图层，只显示当前语种的文字图层 + 所有非语言图层
   - 验证各语种导出图片的尺寸是否一致

**多语种图片的设计稿图层结构示例**：

设计稿中一个多语种按钮可能的图层结构：
```
├── Button Group
│   ├── [👁] button-bg (pixel) ← 非语言图层，所有语种共用
│   ├── [👁] button-border (shape) ← 非语言图层，所有语种共用
│   ├── [👁] EN Text (type: "Start Game") ← 英语图层
│   ├── [🚫] DE Text (type: "Spiel starten") ← 德语图层（隐藏）
│   ├── [🚫] FR Text (type: "Commencer") ← 法语图层（隐藏）
│   └── [🚫] ES Text (type: "Iniciar juego") ← 西语图层（隐藏）
```

导出时分别操作：
- 英语版：显示 `EN Text`，隐藏其他语言文字图层 → 导出合并图为 `button_en.png`
- 德语版：显示 `DE Text`，隐藏其他语言文字图层 → 导出合并图为 `button_de.png`

### 第七步：调用 ps-export 导出图片

根据图片导出清单，使用 `list-layers` skill 读取图层结构，再通过 `ps-export` skill 从设计稿中导出所需的 PNG 图片。

**调用要求**：
1. 将清单中的每张图片对应到设计稿的具体图层（通过读取图层结构匹配）
2. 单独导出图层时 ps-export 会自动裁剪透明区域，确保导出图片只包含实际内容
3. 导出到一个临时目录，后续再移动到项目正确位置
4. 对于替换类图片，确保导出的图片与原图用途一致（可通过图层名称、位置、尺寸辅助判断）
5. **对于背景图，必须严格按照隐藏图层清单设置可见性后再导出**，确保代码中已独立渲染的元素不出现在背景图中

**背景图导出专项规则**：

背景图导出是本 skill 中最容易出错的操作，必须格外谨慎：

1. **核心逻辑：基于代码分析确定隐藏图层**：
   - 分析项目代码，找出背景图覆盖区域内所有已通过 HTML/CSS/JS 独立实现的元素
   - 将这些元素对应的设计稿图层设为 `visible: false`
   - **其余图层保持设计稿原始可见性不动**（不要主动隐藏未分析到的图层，避免遗漏装饰性元素）
   - 同时隐藏不属于该背景图范围的其他顶层图层组（避免其他区域内容渲染进来）

2. **使用 composite 模式**：背景图通常由多个图层合成（渐变+纹理+装饰等），必须用合并导出模式

3. **可见性设置的三步法**：
   ```
   步骤一：分析代码 → 确定哪些图层对应的元素已在代码中实现
   步骤二：将"已在代码中实现"的图层设为 visible: false
   步骤三：将不属于该背景图范围的其他顶层图层组设为 visible: false
   （其余图层保持原样，不主动修改其可见性）
   ```

   对应的 `ps-export` 调用：
   ```powershell
   # 隐藏代码中已独立实现的元素 + 隐藏不属于该背景图范围的其他顶层图层组
   powershell -ExecutionPolicy Bypass -File "$env:USERPROFILE\.kiro\skills\ps-export\ps-export.ps1" `
   ```

**导出模式快速判断**：

| 图层类型 | has_effects | 导出模式 | 说明 |
|----------|-------------|----------|------|
| 图层组（group） | 任意 | composite | 组内多图层需合并渲染 |
| 单图层（pixel/shape） | false | individual | 直接导出，效率最高 |
| 单图层（pixel/shape） | true | composite | individual 会丢失效果，必须用 composite |
| 背景图（多图层合成） | 任意 | composite | 需合并多图层 + 隐藏去重图层 |
| 需去重的普通图片 | 任意 | composite | 需隐藏组内子图层后合并导出 |

**含图层效果的图层必须使用 composite 模式导出**：

当图层的 `has_effects: true` 时（含投影、发光、描边、渐变叠加等效果），**禁止使用 individual 模式**（`layer.composite()` 单图层导出会丢失效果），必须改为 composite 模式导出：

1. **检测**：导出前检查目标图层是否 `has_effects: true`
2. **导出方式**：根据代码和需求判断需要隐藏哪些其他图层，然后使用 `psd.composite()` 整体合成导出
   - 隐藏不属于该图片的其他图层
   - 隐藏代码中已独立实现的元素（同背景图去重逻辑）
   - 保留该图层及其效果所依赖的上下文图层（如投影需要下方图层作为参考）
3. **裁剪**：composite 导出后图片为画布大小，需要按目标图层的 bbox 区域进行裁剪（使用 Pillow crop）
4. **效果依赖注意**：某些效果（如投影）会超出图层本身的 bbox 范围，裁剪时需要适当扩大裁剪区域（上下左右各扩大 20-50px），避免截断效果

```powershell
# 示例：composite 导出后裁剪到目标图层区域（含效果溢出边距）
# 使用文件写入工具创建临时 .py 文件 _temp_crop_layer.py，内容如下：
```

```python
# _temp_crop_layer.py
from PIL import Image
import sys, json

img_path = sys.argv[1]       # composite 导出的全画布图片
output_path = sys.argv[2]    # 裁剪后的输出路径
# bbox: [left, top, right, bottom] 从图层结构 JSON 中获取
left, top, right, bottom = int(sys.argv[3]), int(sys.argv[4]), int(sys.argv[5]), int(sys.argv[6])

# 扩大裁剪区域以保留效果溢出（如投影）
padding = 30
img = Image.open(img_path)
crop_left = max(0, left - padding)
crop_top = max(0, top - padding)
crop_right = min(img.width, right + padding)
crop_bottom = min(img.height, bottom + padding)

cropped = img.crop((crop_left, crop_top, crop_right, crop_bottom))

# 再用 getbbox 去除多余透明区域
bbox = cropped.getbbox()
if bbox:
    cropped = cropped.crop(bbox)

cropped.save(output_path)
print(f"✅ 裁剪完成: {cropped.size[0]}×{cropped.size[1]}")
```

**禁止从全页面合成图中裁切独立元素图片（严格执行）**：

导出清单中的每张图片必须**单独**通过 `ps-export` skill 导出（设置对应的 `-Hide` 和 `-Export` 参数），**绝对禁止**以下取巧做法：

1. 先导出一张全页面/全区域 composite 合成图，然后用 Pillow 从中 crop 出按钮、图标、小图片等独立元素
2. 从 bg.png（页面背景图）中裁切某个区域作为独立图片使用

**为什么禁止**：
- 全页面合成图中包含所有可见图层的合成结果（背景 + 文字 + 按钮 + 装饰等），从中裁切的区域必然带有背景内容和其他叠加元素，无法得到透明底的纯元素图片
- 裁切坐标基于估算，不精确，且裁切后再 resize 会导致图片模糊
- 违反了「每张图片必须有明确的图层对应关系」原则

**正确做法**：对每张需要导出的图片，单独调用 `ps-export` skill：
- 通过 `-Hide` 参数隐藏所有不相关的图层
- 只保留目标图层组/图层可见
- 使用 composite 模式导出后，通过 bbox 裁剪到目标区域
- 最终得到透明底的纯元素图片

```

1. 导出全页面 composite → bg-full.png (750×2480)
2. 用 Pillow 从 bg-full.png 裁切 (350,10,750,120) → small-regist-btn.png
   问题：裁出的图片包含背景内容，不是透明底的纯按钮

✅ 正确做法：
```

- **高度超出**：裁剪图片上下的透明区域
- **宽高同时超出**：同时裁剪四周的透明区域

| ≥ 18.x | ✅ 支持 | 使用 Node.js 版（`@playwright/test`） |
| 16.x | ⚠️ 旧版可能支持 | 尝试 Node.js 版，失败则回退 Python 版 |
| < 16.x 或无 Node | ❌ 不支持 | 使用 Python 版（`playwright` pip 包） |

**方案一：Node.js 版（Node ≥ 18 时优先使用）**

```powershell
# 检查是否已安装
npx playwright --version

# 未安装则安装
npm install -D @playwright/test
npx playwright install chromium
```

**方案二：Python 版（Node 版本不支持时使用）**

使用 design-to-code 虚拟环境安装 Playwright Python：

- Node.js 版安装失败（网络问题）时，尝试 `yarn add -D @playwright/test` 或 `pnpm add -D @playwright/test`
- Python 版如果 `playwright install chromium` 下载缓慢，可设置镜像：`PLAYWRIGHT_DOWNLOAD_HOST=https://npmmirror.com/mirrors/playwright`

#### 启动项目并截图

1. **启动开发服务器**：

   **端口选择规则**：默认使用 `8081` 端口启动，启动前检查端口是否已被占用，如果被占用则递增尝试 `8082`、`8083`...，直到找到可用端口。

   ```powershell
   # 1. 从 8081 开始查找可用端口
   $PORT = 8081
   while (Get-NetTCPConnection -LocalPort $PORT -ErrorAction SilentlyContinue) {
     $PORT++
   }
   Write-Host "✅ 使用端口: $PORT"

   # 2. 使用找到的可用端口启动开发服务器（根据项目类型选择命令）
   npm run dev -- --port $PORT    # Vite
   npm run serve -- --port $PORT  # Vue CLI
   $env:PORT=$PORT; npm start     # CRA / 通用
   ```

   **注意事项**：
   - 不同构建工具指定端口的方式不同，需要根据项目实际使用的工具选择正确的命令参数
   - 启动后记录实际端口号，后续 Playwright 截图脚本中使用该端口

2. **截图前检查**（确认页面正常后再执行截图）：

   **截图前必须确认页面处于正常可验证状态，避免截到错误/异常页面。**

   - **页面加载检查**：
     - 确认页面 HTTP 状态码为 200（非 404、500 等错误）
     - 确认页面无白屏/空白（至少有基本 DOM 结构渲染出来）
     - 确认控制台无阻断性 JS 错误（如 `Cannot read property of undefined` 导致整个页面崩溃）

   - **图片资源加载检查**：
     按验证清单逐一检查本次修改/新增的图片是否加载成功：
     ```javascript
     // 批量检查图片加载状态
     const imageChecks = await page.evaluate(() => {
       const results = [];
       
       // 检查所有 img 标签
       document.querySelectorAll('img').forEach(img => {
         if (!img.complete || img.naturalWidth === 0) {
           results.push({ type: 'img', src: img.src, status: '❌ 加载失败' });
         }
       });
       
       // 检查 requestfailed 中收集的失败资源
       return results;
     });
     
     if (imageChecks.length > 0) {
       console.log('⚠️ 以下图片资源加载失败：');
       imageChecks.forEach(r => console.log(`  ${r.status}: ${r.src}`));
       // 图片加载失败时不应继续截图验证，先排查路径问题
     }
     ```

   - **开发服务器编译检查**：
     - 确认开发服务器已完成编译（无 `compiling...` 或 HMR 更新中的状态）
     - 如果启动后立即截图可能截到编译中间状态，等待 `networkidle` + 额外延时

   **如果检查发现问题**：
   - 图片 404 → 回到第八步检查文件路径、文件名大小写、import 路径是否正确
   - JS 报错 → 检查代码语法或依赖问题
   - 页面白屏 → 检查开发服务器日志、路由配置

3. **编写临时截图脚本** `_playwright_verify_temp.mjs`：

   **视口尺寸必须根据第二步判断的端类型设置**：

   ```javascript
   import { chromium } from 'playwright';

   let browser;
   try {
     browser = await chromium.launch();
     const page = await browser.newPage();
     
     // ⚠️ 根据端类型选择对应视口尺寸（二选一，不能混用）
     
     // 📱 移动端项目（设计稿宽度 750px）→ 视口 750×1334
     await page.setViewportSize({ width: 750, height: 1334 });
     
     // 🖥️ PC 端项目（设计稿宽度 1920px）→ 视口 1920×1080
     // await page.setViewportSize({ width: 1920, height: 1080 });
     
     // 监听页面错误（资源加载失败等）
     const pageErrors = [];
     page.on('pageerror', err => pageErrors.push(err.message));
     page.on('requestfailed', req => pageErrors.push(`资源加载失败: ${req.url()}`));
     
     const response = await page.goto('http://localhost:PORT/页面路径', { timeout: 30000 });
     if (!response || response.status() >= 400) {
       throw new Error(`页面加载失败，状态码: ${response?.status() || '无响应'}`);
     }
     
     await page.waitForLoadState('networkidle');
     
     // 等待图片加载完成
     await page.waitForTimeout(2000);
     
     // 全页面截图
     await page.screenshot({ 
       path: '_screenshot_result_temp.png', 
       fullPage: true 
     });
     
     // 也可以截取特定区域
     // const element = await page.locator('.target-section');
     // await element.screenshot({ path: '_screenshot_section_temp.png' });
     
     // 输出页面错误信息（如有）
     if (pageErrors.length > 0) {
       console.warn('⚠️ 页面存在以下错误（可能影响截图结果）:');
       pageErrors.forEach(e => console.warn(`  - ${e}`));
     }
     
   } catch (err) {
     console.error(`❌ 截图失败: ${err.message}`);
     process.exit(1);
   } finally {
     if (browser) await browser.close();
   }
   ```

   **视口设置规则**：
   
   | 端类型 | 设计稿宽度 | Playwright 视口 | 说明 |
   |--------|-----------|----------------|------|
   | 移动端 | 750px | 750 × 1334 | 视口宽度与设计稿一致，rem 适配方案下 1:1 还原 |
   | PC 端 | 1920px | 1920 × 1080 | 设计稿即为实际渲染尺寸 |

   **为什么移动端用 750**：移动端设计稿以 750px 宽度输出，Playwright 视口设为 750px 宽度时，项目中 rem 适配方案（html font-size 动态按屏幕宽度计算）会在该视口下 1:1 还原设计稿效果，图片 rem 值 = 像素值 ÷ 100 时正好完美匹配。

   ```python
   import sys

   try:
       with sync_playwright() as p:
           browser = p.chromium.launch()
           page = browser.new_page()
           
           # ⚠️ 根据端类型选择对应视口尺寸
           # 📱 移动端项目（设计稿宽度 750px）→ 视口 750×1334

           page_errors = []
           page.on("pageerror", lambda err: page_errors.append(str(err)))
           page.on("requestfailed", lambda req: page_errors.append(f"资源加载失败: {req.url}"))

           page.wait_for_load_state("networkidle")
           page.wait_for_timeout(2000)
           
           # 全页面截图
           page.screenshot(path="_screenshot_result_temp.png", full_page=True)
           
           # 局部区域截图
           # page.locator(".target-section").screenshot(path="_screenshot_section_temp.png")
           
           # 输出页面错误
           if page_errors:
               print("⚠️ 页面存在以下错误：")
               for e in page_errors:
                   print(f"  - {e}")
           
           print("✅ 截图完成: _screenshot_result_temp.png")

   except Exception as err:
       print(f"❌ 截图失败: {err}")
       sys.exit(1)
   ```

#### 多语言验证（仅多语言项目）

**当本次修改涉及多语种图片时，必须切换至少一个非默认语种进行验证。**

1. **确定验证语种**：
   - 默认语种（通常是英语）必须验证
   - 至少再选 1 个非默认语种验证（优先选文字最长的语种如德语，最容易暴露尺寸问题）
   - 如果有 3 个以上语种，建议至少验证 2-3 个有代表性的语种

2. **切换语言的方式**（按项目情况选择）：
   ```javascript
   // 方式一：通过 URL 参数切换
   await page.goto('http://localhost:5173/activity?lang=de');
   
   // 方式二：通过 localStorage/cookie 切换
   await page.evaluate(() => {
     localStorage.setItem('lang', 'de');
     // 或 document.cookie = 'lang=de';
   });
   await page.reload();
   
   // 方式三：通过页面上的语言切换按钮
   await page.click('.lang-switcher');
   await page.click('.lang-option-de');
   await page.waitForTimeout(1000);
   
   // 方式四：通过 Vue i18n 直接修改
   await page.evaluate(() => {
     const vm = document.querySelector('#app').__vue__;
     vm.$i18n.locale = 'de';
   });
   await page.waitForTimeout(500);
   ```

3. **多语言验证重点**：
   - 各语种图片是否正确加载（路径中语种变量是否正确替换）
   - 各语种图片尺寸是否一致（容器大小不应随语种变化而跳动）
   - 图片中的文字是否显示为正确的语种内容（而非其他语种）
   - 切换语言后布局是否正常（不错位、不溢出）
   - **效果图对比**：
     - 切换到某个语种后的截图，需要与该语种对应的设计稿效果图对比
     - 效果图导出时：显示该语种的文字图层，隐藏其他语种的文字图层，保留所有非语言图层，使用 composite 模式导出
     - 如果设计稿中没有该语种的独立效果图层（只有导出的图片），则只验证图片加载和尺寸一致性，不做效果图对比

4. **多语言截图命名**：

#### 对比验证

**验证目标：确认本次修改/新增的图片在页面中正确显示，而非整页像素级一致。**

整个页面与设计稿之间天然存在差异（字体渲染、动态内容、抗锯齿等），不能直接全页面像素对比。验证应聚焦于**图片本身**。

**验证方式（按优先级）**：

1. **逐图片验证（主要方式）**：
   针对每张本次修改/新增的图片，验证以下内容：
   
   - **图片是否加载成功**：检查页面中图片元素的 `naturalWidth > 0`，或背景图 `url()` 是否返回 200
     ```javascript
     // 检查 img 标签图片加载
     const imgLoaded = await page.evaluate(() => {
       const img = document.querySelector('.target-img');
       return img && img.naturalWidth > 0 && img.complete;
     });
     
     // 检查背景图是否加载
     const bgLoaded = await page.evaluate(() => {
       const el = document.querySelector('.target-section');
       const bgUrl = getComputedStyle(el).backgroundImage;
       return bgUrl && bgUrl !== 'none';
     });
     ```
   
   - **图片尺寸是否正确**：截取图片元素/容器，检查实际渲染尺寸是否与预期一致
     ```javascript
     const imgRect = await page.locator('.target-img').boundingBox();
     console.log(`图片实际渲染尺寸: ${imgRect.width}×${imgRect.height}`);
     // 与预期尺寸对比（允许 ±2px 误差）
     ```
   
   - **图片内容是否正确**：截取图片区域截图，与从设计稿导出的**同一图片**进行像素对比
     ```javascript
     // 截取页面中图片所在区域
     await page.locator('.header-bg-container').screenshot({ 
       path: '_screenshot_section_header_temp.png' 
     });
     ```
     然后将这张局部截图与从设计稿导出的对应图片进行对比（不是和完整效果图对比）

2. **图片内容对比方法**：
   - 将 Playwright 截取的**图片区域截图**与**导出的原始图片**或**设计稿效果图**对比
   - 对于 `<img>` 标签图片：直接截取 img 元素本身，与导出的原始图片 1:1 对比
   - 对于背景图：需要专项验证（见下方）
   - 对比时允许的差异：抗锯齿边缘（±1px）、轻微的颜色色差（<3%）

   **背景图验证专项规则**：

   背景图无法通过简单截取容器来验证内容正确性——因为 Playwright 截取容器时，容器内的子元素（文字、按钮等）会一起被截入，无法单独看到「纯背景」。因此背景图的验证采用以下策略：

   **验证方式一：区域效果图对比（主要方式）**

   将 Playwright 截取的**整个背景容器区域**（含子元素）与设计稿中**同区域的完整效果图**（同样含文字/按钮等所有内容）对比：
   
   - Playwright 截图：容器区域的实际渲染效果（背景图 + 上方的文字/按钮/图标等）
   - 设计稿效果图：同区域的 composite 导出（保持所有图层可见，即设计师交付的完整视觉）
   - 对比重点：**背景部分**是否一致（忽略文字渲染差异和动态内容为空的区域）
   
   这种方式下，如果背景图中**多余地包含了文字/按钮等元素**（去重失败），在截图中会表现为「文字叠文字」「按钮叠按钮」——即同一位置出现双份内容，视觉上非常明显。

   **验证方式二：隐藏子元素后截图（精确验证）**

   当方式一无法明确判断背景图是否正确时（如子元素恰好遮挡了背景中的问题区域），通过 JS 临时隐藏容器内的子元素，只留背景图可见：

   ```javascript
   // 临时隐藏背景容器内的所有子元素，只保留背景图可见
   await page.evaluate((selector) => {
     const container = document.querySelector(selector);
     Array.from(container.children).forEach(child => {
       child.style.setProperty('visibility', 'hidden', 'important');
     });
   }, '.header-section');

   // 截取只有背景图的容器
   await page.locator('.header-section').screenshot({ 
     path: '_screenshot_bg_only_temp.png' 
   });

   // 恢复子元素可见性
   await page.evaluate((selector) => {
     const container = document.querySelector(selector);
     Array.from(container.children).forEach(child => {
       child.style.removeProperty('visibility');
     });
   }, '.header-section');
   ```

   然后将这张「纯背景截图」与导出的背景图文件对比，验证：
   - 背景图内容是否正确（装饰元素完整、渐变正确）
   - 背景图中**没有多余的文字/按钮/图标**（去重是否成功）
   - 背景图的 position/size/repeat 是否正确

   **背景图去重失败的典型表现**：

   | 表现 | 说明 | 原因 |
   |------|------|------|
   | 文字叠文字（重影） | 同一位置出现两份文字，一份清晰一份模糊 | 背景图中包含了文字图层，代码又渲染了一份文字 |
   | 按钮叠按钮 | 按钮位置出现双层视觉 | 背景图中包含了按钮图层，代码又渲染了独立按钮 |
   | 图标重复 | 图标位置颜色加深或出现轻微错位的重影 | 背景图中包含了图标，代码又用 `<img>` 渲染了一份 |
   | 整体偏暗/偏浓 | 页面整体颜色比设计稿更深 | 背景图中包含了半透明元素，与代码渲染的元素叠加后加深 |

   **验证判定**：
   - ✅ 通过：纯背景截图中只有装饰性内容（渐变、纹理、光效、装饰图案），没有任何文字、按钮、图标等 UI 元素的痕迹
   - ❌ 不通过：纯背景截图中出现了文字/按钮/图标等不应出现的内容 → 回到第七步检查 `visibility_changes` 配置，补充遗漏的隐藏图层后重新导出

3. **从设计稿导出效果图（用于对比验证）**：

   验证时需要从设计稿中导出对应的效果图作为对比基准。根据验证范围不同，导出方式也不同：

   ---

   **A. 全页面效果图导出（修改整个页面/新建页面时使用）**

   导出设计稿的完整渲染效果，保持设计稿原始图层可见性不变（即设计师交付时的视觉效果）：

   ```powershell

   # 2. 执行导出（保持设计稿原始可见性，导出完整页面）
   ```

   - `crop_mode: "canvas"` — 输出完整画布尺寸（与设计稿尺寸一致），不裁剪
   - 不设置 `visibility_changes` — 保持设计稿原始状态，所见即所得
   - 如果设计稿中有隐藏的弹窗图层，它们不会出现在效果图中（因为原始就是隐藏的）
   - 输出图片尺寸 = 设计稿画布尺寸（移动端 750×全高，PC 端 1920×全高）
   - **效果保留**：ps-export 使用 Photoshop 原生引擎合成，完整保留设计稿中的各种图层效果（投影、发光、描边、渐变叠加、混合模式、蒙版、剪贴蒙版等），导出的效果图能真实反映设计稿的最终视觉效果

   ---

   **B. 局部区域效果图导出（修改某个模块/只替换几张图片时使用）**

   只导出设计稿中某个区域的效果，需要结合代码分析确定区域范围：

   **步骤一：确定目标区域的图层组和边界**

   从第七步读取的图层结构 JSON 中，找到目标区域对应的图层组及其 bbox（边界框）：

   **步骤二：导出 composite 并裁剪到目标区域**

   ```powershell

   # powershell -ExecutionPolicy Bypass -File "$env:USERPROFILE\.kiro\skills\ps-export\ps-export.ps1" `
   #   "/path/to/design.psd" -Hide "Content Section","Footer Section","Popup Layer"
   # 输出 export.png，重命名为 _design_composite_temp.png

     "/path/to/design.psd" -Hide "Content Section","Footer Section","Popup Layer"

   ```

   ```python
   # 2. 使用文件写入工具创建临时 .py 文件 _temp_crop_region.py，内容如下：
   from PIL import Image
   import sys

   img_path = sys.argv[1]       # composite 导出的全画布图片
   output_path = sys.argv[2]    # 裁剪后输出路径

   left, top, right, bottom = int(sys.argv[3]), int(sys.argv[4]), int(sys.argv[5]), int(sys.argv[6])

   img = Image.open(img_path)
   cropped = img.crop((left, top, right, bottom))
   cropped.save(output_path)
   print(f'✅ 区域效果图裁剪完成: ({left},{top},{right},{bottom}) → {cropped.width}×{cropped.height}')
   ```

   ```powershell
   # 执行裁剪脚本
   ~/.kiro/skills/design-to-code/.venv/Scripts/python.exe _temp_crop_region.py `
     _design_composite_temp.png `
     _design_section_temp.png `
     0 0 750 300

   # 3. 删除临时文件
   Remove-Item -Force _temp_crop_region.py, _design_composite_temp.png -ErrorAction SilentlyContinue
   ```

   **关键点**：
   - `visibility_changes` 中隐藏**不属于目标区域的其他顶层图层组** — 减少干扰，加速渲染
   - **不隐藏目标区域内的任何图层** — 效果图需要保持设计稿的完整视觉效果（包括文字、按钮等所有内容），包括图层样式、混合模式、蒙版等效果都需完整保留
   - `crop_mode: "canvas"` — 导出完整画布后用 Pillow 裁剪，确保坐标准确
   - bbox 坐标从图层结构 JSON 的目标图层组中获取（`left`、`top`、`right`、`bottom` 字段）
   - 如果目标区域不是一个完整的图层组（如"只看某几张图片的区域"），可以手动计算 bbox：取所有相关图片图层的 bbox 的外接矩形
   - **效果保留**：隐藏其他区域图层组不会影响目标区域内图层效果的渲染，composite 会完整合成目标区域内所有可见图层及其效果
   - **不做二次透明裁剪**：效果图按 bbox 坐标裁剪后直接使用，不再执行 `getbbox()` 二次裁剪透明区域。保持 bbox 原始尺寸是为了与 Playwright 截图的区域范围保持一致的坐标对应关系，方便 1:1 对比

   - **效果保留**：弹窗图层中的投影、发光、模糊等效果在 composite 模式下会完整渲染，遮罩的半透明混合效果也会正确合成

   **D. 效果图与 Playwright 截图的对比方式**

   导出效果图后，与 Playwright 截图进行视觉对比：

   | 对比场景 | Playwright 截图 | 设计稿效果图 | 对比重点 |
   |----------|----------------|-------------|----------|
   | 全页面 | `fullPage: true` 全页截图 | 全页面效果图（`_design_fullpage_temp.png`） | 整体布局、图片位置、区块间距 |
   | 局部区域 | `.locator('.section').screenshot()` | 区域效果图（`_design_section_temp.png`） | 该区域内图片内容和位置 |
   | 弹窗 | 触发弹窗后截图 | 弹窗效果图（`_design_popup_temp.png`） | 弹窗内图片和装饰元素 |

   **对比时注意**：
   - 效果图是设计稿的理想状态（完整视觉含文字/按钮/图标等所有内容）
   - Playwright 截图是代码实际渲染结果（文字由 CSS 渲染、动态内容可能为空）
   - 文字渲染差异、动态内容为空等不计入验证误差

   **截图与效果图尺寸对齐**：
   - **移动端（视口 750px）**：Playwright 视口宽度 = 设计稿画布宽度 = 750px，两者宽度一致，可直接 1:1 像素对比
   - **PC 端（视口 1920px）**：Playwright 视口宽度 = 设计稿画布宽度 = 1920px，同样 1:1 对应
   - **局部区域截图尺寸可能与效果图 bbox 裁剪尺寸有偏差**：代码中容器的实际渲染尺寸可能因 padding、margin、border 等与设计稿 bbox 不完全一致，此时以肉眼对比图片内容为主，不做像素级尺寸严格匹配
   - **如果截图尺寸与效果图尺寸差异较大**（超过 10%），需要检查是否定位选择器选错了容器（可能截取了一个更大/更小的父级/子级元素）

#### 验证层次（三层验证）

**Playwright 验证不能只验证单张图片，必须按以下三个层次逐层验证，确保功能整体正确：**

---

**第一层：单张图片验证（必做）**

首先确保每张图片本身是正确的，这是后续验证的基础。逐张验证本次修改/新增的图片：

- **非背景图（`<img>`、小 background-image 无子元素）**：直接截取元素，与导出的原始图片对比
  - 图片是否加载成功
  - 图片尺寸是否正确（±2px）
  - 图片内容是否与导出文件一致

- **背景图**：执行背景图专项验证（隐藏子元素后截图），确认去重成功
  - 背景中无多余的文字/按钮/图标残留
  - 背景内容完整（装饰元素未遗漏）
  - background-position/size/repeat 正确

---

**第二层：功能区域整体验证（必做）**

在第一层确认图片本身没问题后，验证本次修改涉及的**功能模块/区域**在页面中的整体表现是否与设计稿一致。一个功能区域包含代码样式 + 图片的组合体，需要作为整体来验证。

- **截图方式**：截取功能区域对应的容器（含其内部所有内容：背景图 + 文字 + 按钮 + 图片等），得到该区域的完整渲染效果
- **对比基准**：从设计稿中导出同区域的效果图（方式 B，保持所有图层可见）
- **验证内容**：

  | 检查项 | 说明 | 判定 |
  |--------|------|------|
  | 区域位置 | 功能区域在页面中的纵向位置是否正确（不错位、不塌陷） | 与设计稿 bbox 的 top 坐标对比 |
  | 区域尺寸 | 区域整体宽高是否与设计稿一致 | 允许 ±5px 误差 |
  | 内部布局 | 区域内各元素的相对位置关系（间距、对齐、排列方向） | 与效果图对比整体结构 |
  | 元素层级 | 元素是否正确叠放（背景在底层、内容在上层、无遮挡异常） | 无元素异常遮挡或被截断 |
  | 视觉完整性 | 整体视觉是否完整、无缺失、无多余（不多不少） | 与设计稿效果图整体比较 |
  | 显示异常 | 有无溢出、错位、重叠、空白间隙、内容塌陷等问题 | 无可见的布局异常 |

- **示例**：
  ```javascript
  // 截取头部功能区域的整体效果
  await page.locator('.header-section').screenshot({ 
    path: '_screenshot_header_full_temp.png' 
  });
  // 与设计稿头部区域效果图（含所有内容）对比
  // 对比重点：整体布局、元素位置关系、视觉完整性
  ```

- **通过标准**：区域整体渲染效果与设计稿效果图在布局结构、元素位置、视觉完整性上无明显差异（允许的差异：字体渲染细节、动态内容为空、颜色抗锯齿）

---

**第三层：跨区域/全页面验证（按需）**

当修改涉及多个区域或整个页面时，验证各区域之间的关系：

- **区域间距**：相邻区域之间的间距是否正确
- **页面总高度**：全页面高度是否与设计稿一致（允许因动态内容为空导致的合理差异）
- **无区域重叠**：相邻区域没有意外的重叠或间隙
- **截图方式**：全页面截图 vs 设计稿全页面效果图

---

**三层验证的执行规则**：

| 层次 | 何时执行 | 不通过时 |
|------|----------|----------|
| 第一层：单张图片 | **始终执行** | 进入第十步重试流程（重新导出/修正路径/调整尺寸） |
| 第二层：区域整体 | **第一层通过后执行** | 定位是布局/样式问题，回到第四步修改 CSS 代码 |
| 第三层：跨区域 | 第二层通过后，且修改涉及多个区域 / 新建页面 / 布局调整时执行 | 检查区域间的 margin/padding 或整体结构问题 |

**第一层不通过时**：图片本身有问题（加载失败、内容错误、去重失败等），后续层次无需执行，直接进入重试流程修复图片问题。

**第一层通过但第二层不通过的情况**：说明图片本身没问题，但代码样式（布局、间距、定位等）导致整体显示异常。此时需要回到第四步修改 CSS 代码，而非重新导出图片。

**误差判定**：
- **通过 ✅**：三层验证均通过——单张图片加载/尺寸/内容正确 + 区域整体布局正确 + 跨区域关系正常
- **不通过 ❌**：任一层验证失败

**不计入误差的差异**：
- 文字渲染差异（字体、抗锯齿、行高细微差异）
- 动态内容区域（倒计时、用户数据等）为空
- 非本次修改的区域

**根据修改范围选择验证策略**：

| 修改范围 | 第一层验证 | 第二层验证 | 第三层验证 | 效果图导出方式 |
|----------|-----------|-----------|-----------|---------------|
| 新建页面 | 各区域分别截图对比 | 逐张图片验证 | 全页面截图对比 | A + B |
| 修改某个模块/区域 | 该区域整体截图对比 | 该区域内图片逐张验证 | 不需要（除非影响相邻区域） | B |
| 只替换/新增几张图片 | 图片所在区域整体截图对比 | 逐张图片验证 | 不需要 | B |
| 弹窗/浮层修改 | 弹窗整体截图对比 | 弹窗内图片逐张验证 | 不需要 | C |

**全页面对比（修改整个页面时使用）**：

当本次修改涉及整个页面（如新建页面或全页面改版）时，需要做全页面对比：

1. 从设计稿导出完整效果图（方式 A）
2. Playwright 截取全页面截图（`fullPage: true`）
3. 两张图进行视觉对比，重点关注：
   - 整体布局结构是否与设计稿一致（各区块的位置、大小、间距）
   - 所有图片是否在正确位置且内容正确
   - 背景图是否完整且无多余内容
   - 各功能区域之间的间距和排列是否正确
4. 允许的差异：字体渲染（不同字体/字号细微偏差）、动态内容为空、颜色抗锯齿
5. 误差判定：整体布局和图片无明显偏差即为通过，不做严格像素级百分比对比

> ✅ **第九步完成** → 如果验证全部通过，跳过第十步，直接进入第十一步：清理临时文件。如果有验证不通过的图片，进入第十步：失败重试。

### 第十步：失败重试

当验证不通过时，进入重试流程：

1. **定位问题图片**：
   - 通过局部区域截图逐个检查每张新增/替换的图片
   - 对比每张图片所在区域的截图与设计稿对应区域
   - 精确识别是哪张（或哪几张）图片导致的差异
   - 只对有问题的图片进行重试，已通过的图片不再处理

2. **对比分析差异原因**：

   将 Playwright 截图、设计稿效果图、当前导出的图片三方对比，分析差异的具体原因：

   **A. 图层导出错误（导出了错误的图层/区域）**：
   - 现象：截图中图片内容与设计稿完全不同或部分不同
   - 分析：对比导出的图片与设计稿中对应区域，确认是否选错了图层
   - 修复：重新确认正确的图层路径，修改 `target_layers` 配置后重新导出

   **B. 需要合并多个图层导出（遗漏了相关图层）**：
   - 现象：截图中图片内容缺少某些元素（如背景有了但缺少装饰元素、图标有了但缺少光效）
   - 分析：对比设计稿效果图，确认哪些图层的内容在导出图片中缺失
   - 修复：将遗漏的图层加入 `target_layers`，使用 composite 模式合并导出

   **C. 需要隐藏/显示子图层（可见性设置不正确）**：
   - 现象：
     - 背景图中出现了不该有的文字/按钮（应隐藏的子图层没隐藏）
     - 导出的图片中缺少应该保留的内容（不应隐藏的子图层被隐藏了）
     - 多语种图片中出现了错误语种的文字（语种图层可见性切换错误）
     - 普通图片（图层组导出）中出现了不该有的文字/图标（组内应隐藏的子图层没隐藏）
   - 分析：逐个检查 `visibility_changes` 配置中各图层的显隐状态是否正确
   - 修复：修正 `visibility_changes` 配置，重新导出

   **D. 图片尺寸/CSS 问题**：
   - 现象：图片内容正确但大小不对、位置偏移、被裁剪
   - 分析：对比图片实际尺寸与 CSS 设置的尺寸是否匹配
   - 修复：重新计算尺寸并修改 CSS

   **E. 图片被容器裁剪/溢出**：
   - 现象：图片部分内容不可见，被截断
   - 分析：检查容器的 `overflow`、`max-width`、`max-height` 等属性
   - 修复：调整容器样式

   **F. 图片层级/遮挡问题**：
   - 现象：图片被其他元素遮挡（如被相邻元素覆盖、z-index 不对）
   - 分析：检查截图中该区域是否有其他 HTML 元素覆盖在图片之上
   - 修复：调整 `z-index`、`position`、元素排列顺序

   **G. 图片加载失败/路径错误**：
   - 现象：截图中图片区域为空白或显示为破损图标
   - 分析：检查浏览器控制台是否有 404 错误，确认图片路径是否正确（大小写、相对路径、别名解析）
   - 修复：修正图片引用路径（注意 `@/` 别名、`../` 相对路径、public 目录区别）

   **H. 背景图 repeat/position 问题**：
   - 现象：背景图内容正确但显示位置不对（偏上/偏下/重复平铺）
   - 分析：检查 `background-position`、`background-repeat`、`background-size` 设置
   - 修复：设置正确的 `background: url(...) no-repeat center / cover` 等属性

3. **执行修复**：

   根据分析结果执行对应的修复操作：

   | 原因类型 | 修复动作 |
   |----------|----------|
   | 图层导出错误 | 修改 ps-export 的 `-Export` 参数指定正确图层路径，重新调用 |
   | 需要合并导出 | 将 mode 改为 `composite`，设置正确的 `target_layers` 和 `visibility_changes`，重新导出 |
   | 子图层可见性错误 | 修改 `visibility_changes` 中对应图层的 true/false 值，重新导出 |
   | CSS 尺寸问题 | 重新获取图片尺寸（使用 Pillow），按 `image-sizing-guide` 规则修改 CSS |
   | 容器裁剪 | 修改容器的 overflow/尺寸相关样式 |
   | 层级遮挡 | 调整 z-index 或 DOM 顺序 |
   | 路径错误 | 修正 import/url 路径，确认文件名大小写 |
   | 背景图属性 | 修正 background-position/size/repeat |

   **重新导出时的注意事项**：
   - 重新导出前，先对照设计稿图层结构再次确认图层路径和可见性
   - 如果是合并导出（composite），确认所有应显示的图层都在 `visibility_changes` 中设为 `true`
   - 导出后用 Pillow 检查新图片的尺寸，确认与预期一致
   - 替换到项目中后，确认代码引用路径和 CSS 尺寸同步更新

4. **重新验证**：
   - 修复后再次执行 Playwright 截图验证（可只验证问题区域）
   - 再次对比并判定
   - 如果修复后差异没有减小反而增大，说明修复方向错误，需要**回滚本次修改**并重新分析

5. **重试策略**：

   **逐步排除法**：当一张图片多次重试仍失败时，按以下顺序逐步排查：
   ```
   第 1 次失败 → 检查图片路径和加载是否正常
   第 2 次失败 → 检查 CSS 尺寸和背景属性是否正确
   第 3 次失败 → 检查图层导出配置（是否选对图层、可见性是否正确）
   第 4 次失败 → 尝试不同的导出策略（individual → composite，或调整图层组合）
   第 5 次失败 → 标记为失败，记录详细诊断信息供用户手动处理
   ```

   **回滚机制**：
   - 每次修复前记录当前状态（图片文件 + CSS 代码）
   - 如果修复后验证差异反而增大（偏离设计稿更远），立即回滚到上一次状态
   - 回滚后换一个方向重新分析和修复

6. **重试次数控制**：
   - 每张图片独立计算重试次数
   - **同一图片最多重试 5 次**
   - 超过 5 次仍未通过，标记为失败，停止该图片的重试
   - 继续处理其他图片

## 注意事项

1. **先备份再替换**：替换图片前必须先备份原图，以便验证失败时回滚
2. **尺寸变更连锁**：替换的图片如果尺寸发生变化，必须同步更新代码中所有引用该图片的尺寸设置
3. **路径一致性**：新增图片的存放路径必须与项目已有的资源组织方式一致（如按模块分目录、按功能分目录等）
4. **开发服务器等待**：启动项目后需要等待编译完成再截图，避免截到空白页面或加载中状态
5. **端口规则**：默认使用 `8081` 端口启动开发服务器，启动前检查是否被占用，被占用则递增（8082、8083...）直到找到可用端口
6. **图层效果处理**：ps-export 使用 Photoshop 原生引擎导出，所有图层效果都能完美渲染（投影、发光、描边、渐变叠加、混合模式等），不存在渲染偏差问题
7. **合并导出判断**：当一个视觉元素由多个图层组合而成时（如背景+装饰+文字），需要合并相关图层导出而非单独导出各个图层
8. **不修改无关代码**：只修改与图片相关的代码，不改动其他业务逻辑
9. **验证范围**：Playwright 验证只关注图片相关的视觉效果，不验证交互逻辑和动画
10. **大设计稿处理**：如果设计稿文件很大（>500MB），在开始前提醒用户处理可能需要较长时间
11. **多语种图片尺寸强一致**：多语种图片各语种版本必须保持相同尺寸，如果因文字长度导致尺寸差异，应通过调整文字图层而非改变整体尺寸来解决
12. **多语种验证覆盖**：Playwright 验证多语种图片时，至少验证 1 个主要语种（通常是英语）的效果。如果英语版通过，默认其他语种的非文字部分也是正确的（因为非语言图层相同）
13. **语种遗漏检测**：导出多语种图片后，对比项目支持的语种列表，如果有语种缺少对应图层（设计稿中没有该语种的文字图层），在摘要报告中标注并提醒用户补充
14. **图片图层去重是第一优先级**：导出任何图片（背景图或普通图片）前必须完成代码分析，确认哪些元素已在代码中独立实现。对于背景图，宁可多隐藏一个图层（后续发现缺失再补回），也不要让背景图中出现重复元素导致页面上「文字叠文字」「图标叠图标」的视觉错误。对于普通图片（图层组导出），需要检查组内是否有代码已独立渲染的子图层（动态文字、独立引用的子图片等），同样需隐藏后再导出
15. **图片格式匹配**：替换图片时必须注意原图格式。PSD 导出为 PNG，如果原图是 JPG/WebP 需要转换格式。含透明区域的图片不能转为 JPG。如果格式变更导致文件扩展名改变，必须同步修改代码中的引用路径
16. **透明度保留**：导出的 PNG 图片默认保留 alpha 通道（透明背景），作为背景图使用时确保 CSS 中对应容器没有设置会遮挡透明区域的背景色
17. **禁止 `python -c` 内联多行代码（严格执行）**：在 shell 中执行 Python 代码时，**绝对禁止**使用 `python -c "多行代码"` 的方式，因为 shell 会将多行压缩为单行导致 `IndentationError`。必须使用以下替代方案：

    **方案一（推荐）：使用文件写入工具创建临时 .py 文件再执行**
    ```powershell
    # 先用文件写入工具创建临时 Python 脚本 _temp_script.py，内容如下：
    ```

    ```python
    # _temp_script.py
    from PIL import Image
    import os

    base = '/path/to/images'
    for f in sorted(os.listdir(base)):
        if f.endswith('.png'):
            img = Image.open(os.path.join(base, f))
            print(f'{f}: {img.size[0]}x{img.size[1]}')
    ```

    ```powershell
    # 执行
    ~/.kiro/skills/design-to-code/.venv/Scripts/python.exe _temp_script.py

    # 删除临时文件
    Remove-Item -Force _temp_script.py -ErrorAction SilentlyContinue
    ```

    **方案二：纯单行（仅当逻辑极简时）**
    ```powershell
    # ✅ 正确：真正的单行，无缩进无换行
    python -c "import json;data=json.load(open('file.json'));print(data['canvas_size'])"
    ```

    **绝对禁止的写法**：
    ```powershell
    # ❌ 错误：多行代码放在 -c 参数中
    python -c "
    import json
    data = json.load(open('file.json'))
    print(data['key'])
    "
    ```

18. **所有脚本必须输出可见的进度和结果**：在执行过程中编写的任何临时 Python 脚本或其他脚本（bash、node 等），都必须通过 `print()` / `echo` / `console.log()` 将关键信息输出到 stdout，确保在聊天框中可以直接看到执行进度和结果。具体要求：
    - **进度信息**：长时间操作必须输出进度（如 `[2/5] 正在处理...`）
    - **操作结果**：每个关键步骤完成后输出结果（如 `✅ 已导出 banner-bg.png (750×300)`）
    - **错误信息**：出错时输出具体原因（如 `❌ 图层不存在: Header/Logo`）
    - **数据摘要**：分析 JSON/图片等数据时，将分析结果通过 print 输出（如图片尺寸列表、图层匹配结果等）
    - **禁止静默执行**：不允许脚本执行完毕后没有任何输出，即使操作成功也要输出确认信息
